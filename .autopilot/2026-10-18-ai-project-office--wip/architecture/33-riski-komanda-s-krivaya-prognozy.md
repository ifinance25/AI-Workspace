# 33. Категории рисков, командная оценка, S-кривая, прогнозы расписания

Документ для разработчиков. Кода нет. Дата: 2026-10-28. Основание: бриф, четырнадцатая запись: «Включи указанные ниже пункты в архитектуру» по строкам `30` §8: 78 «Оценки эффективности команды», 39 «RBS рисков», 66 «S-кривая», 115 «Прогнозы расписания». Требования A84-A87, таски 152-155, инварианты И-151..И-155.

Сокращения как в `30` §0. Новые: RBS рисков (risk breakdown structure, дерево категорий риска); PV плановый объём, EV освоенный объём, SPI индекс выполнения сроков, ES освоенное расписание (`09` §7.3); CPM метод критического пути.

## 2. RBS рисков: дерево категорий (строка 39, A84, таск 152)

### 2.1. Данные

- `office_risk_categories` (`tenancy`): `id`, `company_id`, `project_id?` (лист проекта), `parent_id?`, `code`, `title`, `archived_at?`. Глубина не больше трёх уровней.
- Дерево компании по умолчанию (ведёт РПО): «Технические» (требования, технология, качество, интеграции), «Внешние» (заказчик, поставщики, регуляторы, рынок), «Организационные» (ресурсы, финансирование, приоритеты), «Управление проектом» (оценки, планирование, коммуникации), «ИИ» (качество вывода, предвзятость, данные; закрывает `30` ИИ-7), «Безопасность и ПДн».
- `office_risks.category_id`: у кандидата от `cycle` может быть пусто; при принятии риска МП (`registers/edit`) категория обязательна (422 `category_required`).

### 2.2. Где используется

| Место | Что даёт | Кому |
|---|---|---|
| Сессия проработки (`23`) и вопросы ассистента | Обход дерева как чек-лист: «по категории „Поставщики“ рисков нет, проверьте» | МП, команда |
| Реестр рисков, вид «Тепловая карта по категориям» | Вероятность × влияние, сгруппировано по категориям | Видящие реестр (`registers/view`) |
| Опыт прошлых проектов (`23` §5) | Риски и уроки той же категории из закрытых проектов | Только проекты, которые пользователь и так видит (И-151) |
| Кандидаты риска от `cycle` и от прогноза (§5) | Категория предлагается кодом: отклонение сроков → «Управление проектом / Планирование»; метрики ИИ → «ИИ» | МП подтверждает |
| Портфельный виджет W6 (`31`, таск 150) | Число рисков по категориям в портфеле, без текстов | РПО, руководство |

### 2.3. Права

| Клетка | Кто | Ошибки |
|---|---|---|
| `pmo/edit_risk_taxonomy` (дерево компании) | РПО, АдмК | 403 |
| Лист проекта | МП (`registers/edit`) | 409 `category_in_use` при удалении: только архив |

Само дерево не несёт данных проекта; данные класса несёт риск. Заказчику реестр рисков закрыт (`03` §4.2), категории тоже.

## 3. Командная оценка эффективности (строка 78, A85, таск 153)

### 3.1. Из чего складывается

1. **Анкета команды на ретро** (таск 39): 6 вопросов по шкале 1-5: ясность целей, взаимопомощь, нагрузка, качество работы, можно ли говорить о проблемах, работа процесса. Ответ анонимный. Свободный комментарий по желанию.
2. **Командные показатели** из уже хранимых данных (движок `insight`, таск 54): доля задач, закрытых в срок; доля возвратов после ревью; время цикла задачи; стабильность скорости спринта; доля отклонённых пунктов ревью вывода модели. Все показатели **по команде проекта за период**.
3. **Отчёт «Эффективность команды»** (О-К1): динамика по ретро, показатели, темы комментариев. Готовит код; модель только пересказывает темы, без цитат и без угадывания авторов.

### 3.2. Защита людей

| Правило | Как держится |
|---|---|
| Ни одного показателя на человека | Метрики набора `team_effectiveness` в `insight` не принимают измерение `person` и `assignee`: 422 `dimension_forbidden` (И-152) |
| Анонимность анкеты | Ответ хранится без `user_id`; от повторного голоса защищает одноразовый токен, токен стирается при закрытии опроса (И-153). Результат виден только при не меньше чем k ответах (k как в `31` §7.3, по умолчанию 3) |
| Комментарии | Видят МП и команда проекта; РПО и руководство получают только числа. Комментарии проходят `pseudonymize` до показа и до индекса RAG; в индекс идут только с меткой проекта |
| Сырые ответы | Удаляются после подсчёта итога; хранится итог (152-ФЗ: меньше ПДн) |
| Агенты | Агент проекта видит итог как `team`; запрос «кто тянет команду вниз» отклоняет политика вывода (как М-13) |
| Заказчик | Никогда (И-154) |

### 3.3. Права

`team/view_effectiveness`: МП, участники проекта, РПО (только числа). `team/run_survey`: МП. Данные класса `team`.

## 4. S-кривая (строка 66, A86, таск 154)

### 4.1. Расчёт

По `09` §7.3 и P21. Ось времени: недели или месяцы. Линии:
- **План (PV)**: из принятой базы и дат Ганта (таск 93). Правило 0/100 или 50/50 по `ev_method` базы.
- **Освоено (EV)**: из моментов `done` в `office_task_history`.
- **Факт затрат (AC)**: из `office_cost_entries`, если факт введён; иначе линии нет с подписью «факт не введён».
- Призрак прежней базы: при новой базе старая кривая пунктиром.

Без принятой базы экран пишет «база не принята» (409). Числа считает только код, модель их не меняет.

### 4.2. Два вида

| Вид | Единица | Класс | Кто видит |
|---|---|---|---|
| Трудоёмкость | Часы оценок ИСР и доля пакетов | `team` | Команда, МП, РПО |
| Деньги | Валюта базы | `budget` | Только право `budget` (A22): МП, РПО, руководство с назначением |

Заказчику график и кривые закрыты (`03` §4.2). В согласованный отчёт заказчику может войти только процент готовности без денег, через ручное ревью (`25`).

### 4.3. Где показывается

Вкладка «План», подвкладка «Освоенный объём» (`09` §7.5), отчёт О14 (таск 115), виджет портфельного дашборда W11 «S-кривые проектов» (таск 150). Права виджета считает `audience_scope` (принцип `00` №18).

## 5. Прогнозы расписания (строка 115, A87, таск 155)

### 5.1. Два способа и сравнение

1. **По освоенному расписанию**: прогноз длительности = плановая длительность / SPI(t) по ES; прогнозная дата сдачи.
2. **По сети работ**: пересчёт Ганта (CPM) от сегодняшнего дня: сделанное по факту, остаток по оценкам. Выход: прогнозные даты вех, новый критический путь, сдвиг каждой вехи против базы.
3. **Против даты сдачи** (`09` §7.6): запас до даты сдачи в рабочих днях по производственному календарю (таск 93).

Экран показывает оба прогноза рядом и расхождение между ними. Расхождение больше порога (по умолчанию 10 рабочих дней) подсвечивается: значит, оценки или связи в Ганте неточны.

### 5.2. Реакция

- Сдвиг вехи или даты сдачи за порог: событие `schedule.forecast_shifted`, уведомление категории «Сроки» (`25`) МП и РПО; кандидат риска категории «Управление проектом / Планирование» (§2.2).
- Аудитор плана и факта (`20` §1.3) берёт прогноз из этого расчёта, свой не считает.
- Пересчёт: по `task.done`, по смене базы, ночное задание `schedule_forecast` (идемпотентно: повтор даёт тот же результат).

### 5.3. Права

Даты без денег, класс `team`: команда, МП, РПО. Заказчику только прогноз вех в отчёте О15 после ручного ревью. Модель объясняет прогноз словами, но дат не пишет (И-155).

## 6. Права и пути утечки (по постоянному правилу A71, A72)

| Путь | Чем закрыт |
|---|---|
| Оценка команды превращается в оценку человека через узкую команду (2 человека) | Порог k ответов; показатели при команде меньше k не показываются (И-153) |
| Агент собирает из RAG комментарии ретро для чужого проекта | Комментарии проиндексированы с меткой проекта; права до ранжирования (`01`) |
| Деньги через S-кривую в виджете у пользователя без `budget` | Вид «Деньги» имеет класс `budget`; виджет фильтрует `audience_scope` |
| Опыт прошлых проектов по категории риска раскрывает закрытый проект | Поиск только по проектам, видимым запустившему (И-151) |
| Прогноз уходит заказчику до решения МП | Только через ручное ревью отчёта (`25`) |

Инварианты:
- **И-151**: подбор рисков и уроков по категории возвращает только проекты из области видимости запустившего.
- **И-152**: метрики `team_effectiveness` не принимают измерения по человеку.
- **И-153**: ответ анкеты не связан с `user_id`; итог виден при не меньше чем k ответах.
- **И-154**: оценка эффективности команды не попадает к заказчику ни в одном виде и отчёте.
- **И-155**: прогнозные даты, PV, EV и SPI пишет только код; модель их не меняет.
