# 23. Сессии проработки: скилы brainstorming, планирования и допроса, опыт прошлых проектов, сквозная сборка

Документ для разработчиков. Кода нет. Источник: бриф, запись 2026-10-26 (вторая), требование A63; родители A56 (наводящие вопросы, `21` §6), A35 (страж цепочки), A32 (граф и след). Строится поверх `02-agenty-i-modeli.md` (скилы, профили, запуски), `21` §3 (каталог шаблонов, `draft_artifact`), `22` §4-§5 (входы версий, цепочка актуализации), `14` §2.2 (стандартная цепочка), `18` (журнал решений `office_decisions`), `10` §11 и §15 (библиотека решений `office_solutions` в вариантах макетов, сканер обезличивания при пополнении скилов).

Задача из брифа: руководитель проекта вместе с агентом анализирует проект, получает предложения на основе выполненных проектов, отвечает на конкретные вопросы, проводит brainstorming и получает выверенный документ, который соответствует требованиям и видению заказчика. Все артефакты связаны единым сквозным следом.

## 1. Четыре скила и один служебный

| Скил | Имя на экране | По мотивам | Что делает | Фокусная область (A79, на экране «фаза») | Что выходит |
|---|---|---|---|---|---|
| `brainstorming` | «Проработка замысла» | superpowers: brainstorming (сверено с текстом версии 7.0.0 и 6.4.1 из кэша плагинов на машине пользователя) | Понимает замысел и «зачем»: сначала открытые вопросы, по одному, конкретные («расскажите о последнем случае»); короткое меню вариантов только когда человек застрял или просит «предложи»; варианты сравнивает про себя и показывает сравнение, когда оно помогает решить; по мере понимания пересказывает часть замысла (ход `playback`) и спрашивает «что неверно или упущено»; догадки помечает как догадки; в конце независимый читатель проверяет документ и задаёт вопросы | инициация | версия `brief` (блок «Концепция»), допущения, кандидаты требований |
| `grill_me` | «Допрос с премортемом (по Autopilot)» | Autopilot: режим интервью и проход премортема (`phases/2-briefing.md`) | Сначала сам ищет, где идея разваливается, по семи линзам Autopilot: провал («сдано, работает, никто не пользуется: что случилось»), столкновение двух требований, непроверенное («данные откуда-то возьмутся»), цена, условие успеха, «вторая неделя» (рост, дубли, поддержка), второй актор. Потом спрашивает по одному вопросу с рекомендованным ответом и ценой; блокирующие вопросы первыми; факты ищет сам, спрашивает только решения; каждый вопрос привязан к требованию; находка не может удалить или сузить требование (И-69) | инициация, планирование | открытые вопросы, кандидаты рисков, допущения, решения |
| `grilling` | «Допрос по дереву решений (по Matt Pocock grill-me)» | Matt Pocock: grill-me (по памяти, текст не проверен по первоисточнику, В23-1) | Допрашивает по каждой ветке дерева решений, пока не будет общего понимания; разрешает зависимости решений по одной; к каждому вопросу даёт рекомендованный ответ; вопросы по одному; если ответ можно найти в источниках, ищет, а не спрашивает | планирование (задание, архитектура, план) | решения в журнале, уточнённые требования, правки задания |
| `writing_plans` | «План работ» | superpowers: writing-plans (сверено с текстом версии 7.0.0) | Из принятого задания делает план: карта результатов, пакеты работ размером «свой цикл проверки и смысл отдельной приёмки», у пакета критерий готовности (словарь ИСР `acceptance`), что пакет потребляет и что отдаёт (основа связей `fs`), сквозные ограничения задания, список «что вероятнее всего сломается» (кандидаты рисков); самопроверка: каждое требование покрыто пакетом, имена и связи согласованы | планирование | черновик ИСР (`plan.draft_wbs`), связи-кандидаты Ганта (`plan.propose_links`), раздел сводного плана |
| `brief_interview` (служебный) | «Уточнение брифа» | `21` §6 | Закрывает пробелы шаблона задания вопросами | инициация | ответы в документ сессии, черновик задания |

Расхождение с источником (сверка 24, С24-08): первая редакция описывала `brainstorming` как «варианты с рекомендацией, 2-3 подхода, подтверждение каждого раздела»; так устроена версия 6.4.1, а в 7.0.0 варианты считаются подталкиванием и идут только по просьбе. Сессия поэтому поддерживает оба стиля вопроса (`question_style enum(open, choice)`, §2.1), стиль задаёт текст скила; рекомендованный вариант первым обязателен для `grill_me`, `grilling`, `brief_interview` и необязателен для `brainstorming`.

Скил назначает МП проекту (`office_skill_enablements`, с таска 32; в срезе B поставляемые скилы проработки включены для компании по умолчанию), запуск правами назначившего (`02`, `10` §8.1 «От чьего имени»). Модель только через `routing.call`. Новый класс операций `elicitation` (`02` §6.2; сильная модель, среднее усилие, админ меняет) для `brainstorming`, `grilling`, `grill_me`, `writing_plans` и проверки по видению; `search_answer` (быстрая) для поиска ответа в источниках; `brief_interview` остаётся в `draft_text`, как `draft_spec`. Первая редакция писала «сильная, как у `draft_spec`», но `draft_spec` идёт классом `draft_text` (быстрая, низкое усилие), отсюда новый класс (сверка 24, С24-08). Класс `design` (`05` §6 С17) не подходит: он только для макетов через Claude Code.

### 2.2. Ход сессии

1. **Контекст.** Сборщик кодом, без модели: текущие версии артефактов цели и их синхронность (`22` §4.2), открытые вопросы, журнал решений; со среза C реестр допущений, риски, разрывы цепочки и поиск по ядру проекта правами запустившего (`01` §7.3); в срезе B только бриф, отправки и прошлые ответы. При `use_library` (с таска 101, срез G): карточки библиотеки решений и сводка похожих проектов (§4). Чего ещё нет по срезу, сборщик отдаёт строкой «данных пока нет», модель это не угадывает.
2. **Пробелы.** Скил по своей логике строит список того, что не решено (`grill_me` сначала проходит семь линз премортема, `grilling` строит дерево решений с зависимостями). Вопрос, ответ на который уже есть в источниках, не задаётся: агент показывает найденную цитату и спрашивает только «верно?». Блокирующие вопросы (`priority = blocking`) идут первыми.
3. **Вопрос.** Один за раз. Стиль по скилу (§1): открытый вопрос или 2-4 варианта и «свой ответ», «не знаю, решим позже». В стиле `choice` рекомендованный вариант первый, с доводом и ценой. Довод со ссылкой: цитата проекта или карточка библиотеки («SOL-14: в похожем проекте интеграцию с 1С оценили в 40 часов, факт 72»). Вопроса о секретах и учётных данных нет.
4. **Ответ.** Пишется ходом `answer` и абзацем документа `elicitation:<id>` со стороной отвечавшего (Р23-03). «Не знаю» даёт допущение (`office_assumptions`, `22` §2.1, с таска 94, срез C) с датой проверки; до среза C это пункт «Открытые вопросы» документа сессии.
5. **Решение.** Когда ответ закрывает развилку, ход `decision` предлагает запись в журнал решений: `cycle.propose_candidates(kind=decision)` даёт `office_decisions` в `proposed` с уликой на абзац ответа; `accepted` только подтверждением человека (как И-59). Пометку «типовое» для библиотеки ставит МП полем `office_decisions.typical bool` (новое, сверка 24 С24-18).
6. **Пересказ** (`playback`, для `brainstorming` обязателен, для остальных по тексту скила). Когда часть понятна, агент пересказывает её на 200-300 слов (калибровка по тексту superpowers 7.0.0), помечает догадки и спрашивает «что неверно или упущено». Пересказ не ответ: в документ ответов он не пишется, подтверждённое человеком становится ответом.
7. **Синтез.** `draft_artifact` (`21` §3.3) по цели сессии. Входы версии включают версию документа `elicitation:<id>` (`input_kind = document_version`, `22` §4.1). Каждый пункт с цитатой ответа или источника либо с пометкой «предположение модели».
8. **Проверка.** Проверка по видению заказчика (§3) и, по желанию МП, независимый читатель (как «builder check» superpowers и проверка G2 Autopilot): свежий запуск без истории сессии читает документ и задаёт вопросы; вопросы делятся на «уже отвечено» (вписать), «мелкое» (решает исполнитель, помечается) и «к заказчику или МП» (новые вопросы сессии). Расхождения возвращаются вопросами в ту же сессию.
9. **Готово.** Версия документа идёт обычным MR и маршрутом. Сохранение запускает цепочку актуализации (`22` §5).

### 2.3. Режимы

| Режим | Кто отвечает | Где |
|---|---|---|
| `manager` | МП или аналитик | карточки вопросов в чате ассистента рабочего места (`13`) |
| `customer` | заказчик | форма в кабинете заказчика; один вопрос на экран, ответы возвращаются отправкой, как бриф (`21` §5.1) |
| `joint` | МП и заказчик на созвоне | вопросы на экране созвона; ответы фиксирует МП со стороной `team` и пометкой «со слов заказчика»; словами заказчика для проверки §3 служат реплики расшифровки со стороной `customer` (источник созвона, срез D), а не запись МП |
| `solo` | никто | вопросов нет; все пробелы допущениями; для черновика «быстро посмотреть» |

Заказчику не показываются: карточки библиотеки, сводка похожих проектов, внутренние доводы, бюджет (A22). Вопрос в режиме `customer` проходит фильтр видимости до отправки (И-74); ответ возвращается отправкой `office_brief_submissions` (`21` §5.1) и переносится в документ ответов со стороной `customer`. Проверка ИБ 29 (УИБ29-49): фильтр свободного текста ненадёжен, поэтому в режимах `customer` и `joint` сборщик контекста (§2.2 п. 1) работает в `tenancy.audience_scope(customer)`: модель не получает бюджет, внутренние обсуждения, карточки библиотеки и сводку похожих проектов вовсе; вопрос к заказчику это структура (текст вопроса, варианты, цитаты), источник каждой цитаты код проверяет на видимость профилю заказчика до отправки; ответ заказчика идёт в модель блоком данных и не исполняется как указание.

### 2.4. Остановка и бюджет

Сессия останавливается, когда: все пробелы закрыты; человек нажал «достаточно»; исчерпан `budget` (умолчание 15 вопросов, у `brief_interview` 12, 200 тыс. токенов на сессию; калибровка, не цель; Autopilot называет обычным для режима интервью 10-25 вопросов, это тоже ориентир, не потолок). Оставшиеся пробелы уходят в «Открытые вопросы к заказчику» документа.

## 3. Проверка по видению заказчика (Р23-05)

`agents.check_vision(draft_version_id)` (сверка 24, С24-01: первая редакция ставила проверку в `cycle`, но она зовёт модель запуском агента и пишет ход сессии в таблицу `agents`; `cycle` выше себя не пишет). Запуск агента классом `elicitation`; итог сохраняет `cycle.record_vision_check(version_id, items[])` в `office_vision_checks` (`cycle`), чтобы запрет публикации проверял владелец публикаций без чтения `agents`; ход `check` в сессии пишет `agents`.

- **Вход проверяющего (И-70):** только записи со стороной `customer`, выбранные по происхождению, а не по авторству текущего текста: отправки брифа `office_brief_submissions` (неизменные, даже если менеджер потом переписал бриф); абзацы ответов со стороной `customer` в документах `elicitation:<id>`; комментарии `office_comments.side = customer` к опубликованным версиям; со среза C фрагменты источников со стороной `customer` (письма, чаты, реплики созвонов, `01` §2.3) по запросу к теме документа. Решения журнала передаются только цитатой их улики, если улика со стороны заказчика; текст решения пишет команда, это пересказ, и он не передаётся. Пересказ менеджера, запись ответа в режиме `joint`, ход рассуждений сессии и карточки библиотеки не передаются. Сам проверяемый документ передаётся: с ним и сравнивают.
- **Выход:** таблица «высказывание заказчика → пункт документа» со статусами `covered`, `partial`, `missing`, `contradicted`, `extra` (пункт документа, у которого нет основания в словах заказчика и нет пометки «предложение исполнителя»).
- **Что дальше:** `missing` и `contradicted` возвращаются вопросами в сессию; `extra` требует пометки «предложение исполнителя» или удаления; документ не уходит заказчику, пока есть `contradicted` (МП подтверждает с причиной, иначе 409 `vision_contradicted`, И-71).
- **Где видно:** вкладка «Соответствие» у версии документа; итог пишется ходом `check`.

Проверка повторяет `07-slepaya-proverka.md` по методу, только для документов проекта, а не для этой архитектуры.

## 4. Опыт выполненных проектов (Р23-04)

### 4.1. Библиотека решений

`office_solutions` (`agents`, есть в `03`; таблица появляется в таске 53 среза C для шаблонов страниц, `09` §2.1) получает вид `kind = project_case` рядом с `page_template` и решениями макетов, и поля: `title`, `problem`, `context json {project_type, domain, size_band, stack[]}`, `decision`, `outcome`, `numbers json {estimate, actual, unit}`, `origin_project_id`, `origin_refs json` (идентификаторы узлов `14` §3.1; видны только тем, у кого доступ к исходному проекту), `anonymized bool`, `state enum(proposed, approved, retired)`, `approved_by` (РПО).

Откуда карточки:
- уроки с `publish_to_library` (`22` §2.1, `office_lessons`);
- итоговый отчёт проекта (`final_report`): раздел «что повторить, что изменить»;
- решения из журнала решений, помеченные МП «типовое».

Перед публикацией сканер обезличивания предлагает правки (имена из паспортов, организации, адреса, ключи `REQ`, n-граммы требований), человек правит, РПО одобряет. Сверка 27 (У27-05): `numbers.unit` только часы, дни, штуки или доли; денежная единица и суммы в тексте карточки (детектор валют, как проверка 8 `26` §5.3) дают 422 при предложении карточки, потому что одобренную карточку читают все сотрудники компании, а деньги видит только клетка `plan.budget/view` (A22, И-73). Без одобрения карточка видна только внутри исходного проекта. Сверка 24 (С24-14): в `10` §15 этот сканер описан внутри пополнения скилов «с внедрений», а оно отложено до D04; переиспользовать нечего, сканер строится в таске 101. Библиотека остаётся внутри компании: в общую библиотеку между установками карточки не уходят (это и есть отложенная часть D04).

### 4.2. Похожие проекты

`insight.similar_projects(project_id) -> {bucket, n, median_duration, estimate_vs_actual, top_risk_kinds[], median_change_requests, refs[]?}`: близость только по полям паспорта и профиля (тип, домен, размер, стек). Вектор ядра брифа не используется: сравнение векторов брифов разных проектов это межпроектный поиск, отложенный D01 (И-32; сверка 24, С24-14). Без доступа к проекту ссылки `refs` пусты, отдаются только агрегаты группы и виды рисков, без текстов. Порог показа: не меньше трёх похожих закрытых проектов в группе (калибровка, не цель), иначе «мало данных» (иначе по числам можно узнать конкретный проект). Можно ли показывать МП агрегаты по проектам, к которым у него нет доступа, решает пользователь (В23-5); до ответа сводка видна только РПО и наблюдателю отдела и компании.

Сверка 27 (У27-04, И-100): группа для агрегата считается только по закрытым проектам, к которым у зрителя нет доступа, и порог три применяется к ним; проекты, к которым доступ есть, показываются отдельно ссылками `refs`. Иначе МП с доступом к двум из трёх проектов группы вычислил бы третий. `estimate_vs_actual` это отношение часов, денег в сводке нет (A22). Медианы и доли округляются до 5 процентных пунктов (калибровка, не цель), сводка пересчитывается не чаще раза в сутки, чтобы разность до и после закрытия нового проекта не давала его чисел.

### 4.3. Как скилы это используют

- `brainstorming`: «в похожих проектах выбирали так, итог такой» как довод к варианту.
- `grill_me`: виды рисков, частые в похожих проектах, как темы премортема.
- `writing_plans`: факт против оценки похожих пакетов как поправка к ориентиру; часы в ИСР ставят исполнители (A22), ориентир виден только МП и выключен по умолчанию до ответа на `21` В-5.
- `grilling`: решения библиотеки как готовые варианты ответа.

## 5. Сквозной след

Стандартная цепочка `14` §2.2 получает начало: звено 0 «Основание» принимает абзацы ответов `elicitation:<id>` и отправки брифа, звено 0а решения журнала. Цепочка целиком (хранилище каждого ребра по правилу «одно ребро, одно хранилище владельца», `14` Р14-01, И-37):

| 0а | Решение журнала | `decided_in` (требование → решение; имя уже есть в `14` §3.2), решение `cites` ответ | `office_decisions.requirement_id`, `office_requirements.internal_decision_id` (есть); улика решения `office_decisions.evidence_id` |

Сверка 24 (С24-09): `office_trace_links.target_type` не расширяется. Первая редакция вводила ребро `decided_by`, но это имя уже занято колонкой `office_trace_links.decided_by` (кто решил судьбу ссылки, `14` §3.4), а связь «требование → решение» уже хранится колонками решения и описана ребром `decided_in`. `planned_in` ложится на существующий тип `wbs_item`; `reports_on` и `learned_from` это проекции входов версий и структурных колонок, без новых строк следа. Страж цепочки (`14` §6) получает два вида разрыва-подсказки: `requirement_without_basis` (требование без звена 0; улика с причиной `manual` и текстом по И-42 считается основанием) и `decision_without_answer` (решение без улики ответа, созвона или письма). Где след виден не всем: карточка библиотеки показывает `origin_refs` только имеющим доступ к исходному проекту, для остальных цепочка заканчивается на карточке; это следствие прав, а не разрыв.

Порядок по умолчанию идёт вперёд по срезам, кроме мест, отмеченных «данных пока нет» в последней колонке; ни один шаг не ждёт входа молча.

Сверка 27 (С27-25). Колонка «Кто принимает» для видов с `review_policy = manual_items` (`25` §6.1: `spec:*`, `plan:*`, `gate:*`, `final_report*`, `status_report:customer`, `act:stage-*` (A79: было `act:phase-*`)) с подсрезом C2 (таск 104) означает очередь «На ревью» по пунктам перед слиянием MR агента и перед маршрутом прямой версии (И-80). В B2, до таска 104, прямые версии `draft_artifact` идут на маршрут с прежней проверкой «предположение модели» (`03` §3.2). Агенты, собирающие шаги 4, 10, 12, 16, 17, ищут в области аудитории вида (`internal`, И-87), а не во всех правах назначившего.
