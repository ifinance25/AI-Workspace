# 46. Ручная валидация находок прогона

Документ для разработчиков. Дата: 2026-10-31. Основание: слова пользователя G129-G133, таск 187. Сверка идёт с архитектурой офиса PM Workspace: `10` (поставка, прогоны, находки), `14` §6 (страж цепочки), `25` §6 (ручное ревью), `28` (суверенность данных), §10 ниже. Архитектура QA (`FACT/QA/Архитектура_QA`) дала только имена этапов жизни находки ради совместимости с будущим `qa-platform`, основанием она не является. Это первая часть модуля `delivery` (`10` §1, §5, §6, §16), построенная раньше срока: сверка документов двумя LLM-агентами (ПМИ с ФТТ) даёт находки, проверяющий ставит по ним статус, платформа хранит решения, пишет markdown и считает статистику.

## 2. Данные

- `office_validation_runs`: прогон, ключ `run_key`, вид источника (`doc_review`, `stand_run`), отпечаток пакета.
- `office_validation_findings`: находка, `reason_key`, текущие `review_status` и `lifecycle`, номер решения `decision_seq`, полный текст в `payload`. Поля `scenario_id`, `step_id`, `failure_key`, `task_id`, `check_finding_id` пусты и ждут таска 34.
- `office_validation_decisions`: журнал. Уникальны `(finding_id, seq)` и `(finding_id, request_key)`: первое ловит одновременную правку (409), второе двойное нажатие.
- `office_validation_edits`: правки. Состояния `proposed`, `queued`, `applied`, `rejected`.
- `office_validation_assets`, `office_validation_policy`, `office_validation_exports`.

Соответствие `office_check_findings` (`10` §5.1): совпадают `reason_key`, `evidence`, `task_id`, обязательная причина снятия, роли. Расходятся: у находок сверки документов нет сценария, `severity` на русском (высокая, средняя, низкая переводятся в `blocking`, `significant`, `hint` без права красить сверку), состояний три, а нужно четыре.

## 3. Статусы

| Кнопка | `review_status` | `lifecycle` | Правки | Причина |
|---|---|---|---|---|
| Подтверждено | `confirmed` | `new → confirmed` | `queued` | не нужна |
| Отклонено | `rejected` | `→ rejected` | `rejected` | код и пояснение |
| На уточнение | `needs_info` | без изменений | без изменений | пояснение |
| Правки внесены | `confirmed` | `submitted`, затем `fixed` | `applied`, нужна версия документа | не нужна |
| Вернуть в разбор | `new` | `→ reopened` | `queued` | не нужна |

Дополнение к контракту: переход `reopened → confirmed`, иначе вернувшуюся находку нельзя подтвердить. Состояние `closed` недостижимо: оно требует нового прогона сверки (§14.4), подтверждающего тестирования пока нет.

Статистика: «Валидация пройдена» = подтверждено + отклонено. «Правки внесены в документы» = находки в этапе `fixed`; отдельно счётчик правок. Определение первое, пользователь не уточнял, вопрос В46-1.

## 4. Права и пути утечки

| Путь | Защита |
|---|---|
| Заказчик | 403 на всё, включая снимки, статистику, выгрузку |
| Чужой проект | 404, `project_id` в каждом запросе, снимок проверяется по цепочке проект, прогон, файл |
| Путь к файлу | Клиент пути не передаёт. Адрес строится из номеров и имени из базы, только PNG и PDF, `nosniff`, без символических ссылок |
| Загрузка архива | Белый список имён, отказ по ссылкам и повторным именам, пределы 120 МБ архив, 150 МБ распакованный, 1000 файлов, проверка сигнатур, распаковка во временную папку |
| Секреты и персональные данные | Сканер по образцам (почта, телефон, ключи, `password=`, ФИО) проверяет пакет, причины решений и итог выгрузки. В файлах только роль и условный номер автора |
| Выгрузка | Только markdown и журнал, `data_class: team`, каждая выгрузка в журнале |
| Удаление проекта | С прогонами только МП и администратор, затем удаляется папка |

Сканер по образцам. Он не заменяет псевдонимы из `28` §5: ФИО без отчества и названия организаций он не поймает.

## 5. Файлы

Рядом с базой: `office_validation/p<проект>/r<прогон>/` с `findings/R4-001.md`, `journal.jsonl`, `summary.md`, `img/`, `docs/`. В папку проекта панели класть нельзя: проект офиса с ней не связан (Б43-04), файлы читались бы по чужим грантам. Текст находки стоит в огороженных блоках, а над ними пометка, что это данные, а не инструкция.

## 6. Сервер tatnet

Контур `fakt` на VPS: nginx на 80 и 443, базы знаний и MCP. Новый контейнер `fakt-runs` в своей внутренней сети без выхода в интернет, том только `/srv/fakt/validation`, корпус базы знаний и реестр ключей ему не подключаются. Адрес `runs.pm-workspace.ru`, вход паролем панели. Режим `office_only` не подключает файлы проектов, загрузки, терминал SSH, WebSocket чата, привязку Telegram и прокси базы знаний. Файлы развёртывания: `deploy/tatnet-office/`, инструкция `docs/deploy-tatnet-office.md`. Состояние на 2026-11-01: контейнер, данные, ночные копии и пакет прогона № 4 на сервере, публичного адреса нет (нет DNS-записи, сертификата и подключения к nginx контура), доступ через SSH-туннель `open-tunnel.sh`.

### Противоречие (нужно решение)

1. **Дом модуля. Решено 2026-10-31: вариант 1, оставить в `delivery` (слово пользователя «1»).** Половина находок по смыслу разрывы цепочки, их дом `cycle`. Модуля `cycle` и ядра требований `REQ-NNN` в коде нет (срез C), у находок нет ключей требований. Когда `cycle` появится, находки вида «не проверяется» станут разрывами `no_test` через мост `chain_gap_id`, решения и причины перенесутся. Колонки `chain_gap_id` до этого нет. Отвергнутая альтернатива: ждать срез C и строить сразу на `cycle`.
2. **Причины.** Коды отклонения взяты из ручного ревью (`25` §6.4), причины снятия разрыва другие (`14` §6.5: вне скоупа, уже покрыто, отклонено заказчиком, другое). При переходе на `cycle` нужна таблица соответствия.
3. **Заказчик.** `10` §16 показывает заказчику цвет сверки, сервис не показывает ничего. Решается вместе с таском 34, когда у сверки появится цвет.
