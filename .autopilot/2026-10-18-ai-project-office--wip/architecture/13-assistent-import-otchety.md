## 1. Ассистент офиса (A25, A28)

### 1.1. Граница с чатом Claude Code (A23)

Ассистент это панель «Спросить по проекту» (04 §7), выросшая до агента с инструментами; `knowledge.ask` остаётся быстрым и запасным путём (1.8). Доступен всем 12 ролям, всегда в одном текущем проекте (П9, P04).

| | Чат Claude Code (`/`, темы бота) | Ассистент офиса |
|---|---|---|
| Назначение, кто | Код в `PROJECTS_DIR`; команда | Вопросы и операции по проекту офиса; все роли |
| Где | `src/claude`, `src/bot` | `agents` (профиль `assistant`), `ui`, доставка `channels` |
| Транспорт | `ClaudeBridge`, сессии чата | `ClaudeBridge` SDK, ветка офиса, ключ `office-assistant:<thread_id>` |
| Песочница | Джейл чата, `confine_root` на проекты (A23) | Джейл запуска: пустой `runs/<run_id>`, `--unshare-net`, выход к прокси модели и к MCP офиса через сокет |
| Инструменты | Файлы, Bash, git | Только `mcp__office__*`; список разрешённых в мосту плюс файрвол PreToolUse |
| Данные офиса | Не монтируются; только личный MCP-токен, добавленный самим пользователем (02 §7) | MCP с правами «человек ∩ профиль», проверка на каждом вызове |
| Ключ, след | Как у чата; история чата | Ключ компании через прокси `routing`; `office_assistant_messages`, `office_agent_run_log`, `office_audit` |

Прямой API без джейла не выбран до замера (ADR-04, 02 О2); контракт инструментов от транспорта не зависит, ход может перейти на `anthropic_http` (12 §2.2) без смены таблиц.

### 1.2. Ход диалога

1. Сообщение пишется в `office_assistant_messages` и ставит задание `assistant_turn` с ключом `(thread_id, message_id)`; повтор доставки второго хода не даёт.
2. `AssistantRunner` (`agents`) открывает запуск (`agent=assistant`, `trigger=chat`, `on_behalf_of=user`), берёт строку класса `assistant` и резерв `routing`.
3. Тёплая сессия SDK живёт 10 минут простоя (К27); пул вне слотов агентов (02 §3.3): 512 МБ, до 4 на сервер (доп.); пул занят: холодный старт или быстрый путь.
4. Контекст: конституция по области актора до 800 токенов (01 §7.5); профиль и инструменты до 3 000; сводка и последние сообщения до 1 500; вложения и контекст страницы до 3 000, остальное инструментами. Потолок хода 40 тыс. токенов входа и 8 вызовов инструментов (доп.).
5. Проверка 01 §7.4 без модели: каждая `[n]` указывает на фрагмент, прочитанный в этом ходе; фраза без ссылки помечена «вывод модели»; кавычки сверяет `verify_quote`.
6. Предложения действий становятся строками `office_assistant_actions` и карточками (1.5).
7. Токены идут эфемерными кадрами WS владельцу; итог сообщением и `assistant_message.created`; `settle` по факту.

Смена проекта открывает новый диалог: история одного проекта в контекст другого не попадает. `member.removed` закрывает диалоги актора в проекте и гасит тёплую сессию.

### 1.5. Подтверждение действий

`propose_action(op, params, reason)` не исполняет операцию: создаёт строку `office_assistant_actions` и карточку (что, над чем, кому будет видно, резерв расхода, превью последствий 04 §7 где есть). Если в ходе читался недоверенный материал (письмо, файл заказчика, страница браузера), карточка несёт пометку «предложено после чтения внешнего материала» (02 §10).

Состояния: `proposed` → `confirmed` (нажата кнопка) → `executed` или `failed`; `proposed` → `rejected`; `proposed` → `expired` (30 минут, доп., или новый ход отменил).

1. Подтверждённая операция исполняется от имени человека (`actor=user`, в аудите `via=assistant` и `run_id`), его правами на момент нажатия; ключ идемпотентности `action_id`.
2. Параметры заморожены отпечатком `params_sha`; правка даёт новую карточку.
3. Уровень C (`publish`, `approve_step`, `return_step`, `accept_spec`, `merge_doc_mr`, `approve_task`, `hand_to_team`, ручное слияние MR кода, `signed`, утверждение макета, приём базы, решения по кандидатам, противоречиям и разрывам цепочки (14 §6.13) с правилом 409 `not_viewed`, удаление источника, участники, админка): карточка содержит только ссылку на экран с открытым объектом.
4. Почта: B подтверждается только по ссылке в веб (подделка отправителя). Telegram и Макс: кнопкой клавиатуры; сервер сверяет привязку нажавшего с владельцем карточки.

Дополнение 2026-10-27 (проверка ИБ 29, УИБ29-33). Операции уровня B с внешним эффектом (`reply_letter`, `send_chat_reply`, встреча с внешними гостями) подтверждаются только в веб-сессии с показом полного текста и получателей (И-138); кнопка в Telegram или Максе ведёт в веб. Перед исполнением `channels` сверяет классы черновика по провенансу хода с классами получателя. Почта ящика ассистента принимает отправителя только при выровненном DMARC (подпись DKIM домена из поля From); ответ уходит только на адрес учётки, `Reply-To` игнорируется.

`src/bot`: темы форум-группы остаются чатом Claude Code, личный диалог учётки с привязкой офиса идёт в `channels.on_update` к ассистенту. Учётка только офиса (в том числе заказчик) не попадает в обработчики чата Claude Code даже при совпадении с `ALLOWED_USER_IDS`: проверка привязки первая, обязательный тест. Дополнение 2026-10-23, A41-A45 (18 §1.6, §5.4; 05 §9 С133): привязанный проектный чат уходит `channels.route_update` раньше личного диалога; ассистент как агент в группе молчит (Р13-04), а бот как транспорт публикует в группе только уведомление о привязке, ответы на `/office_id`, `/office_bind` и текст, отправленный человеком из подписи с `params_sha` (И-56); обязательный тест: заказчик из проектной группы не попадает в обработчики чата Claude Code.

Форма ответа по каналу (`settings.assistant_channels` компании, `tenancy`): `full` (с цитатами; умолчание для веба и расширения), `no_quotes` (своими словами со ссылками на места; умолчание для Telegram, Макса, почты до юриста), `link_only` («ответ готов» и ссылка; всегда для проекта с `export_ban=all_external`). Меняет админ компании с записью в аудит.

Дополнение 2026-10-26 (сверка 27, У27-11, У27-12; И-88). Ответ во внешнем канале подчиняется той же планке классов, что уведомления (`25` П-4, И-77): если в ходе использованы фрагменты или факты классов `budget` или `management_chat`, Telegram, Макс и почта получают `link_only` при любой настройке компании («ответ содержит закрытые данные, откройте в платформе»). В закрытом контуре мессенджеры для проекта выключены. Форма `no_quotes` «своими словами» не считается обезличиванием: пересказ суммы это сумма.

Дополнение 2026-10-27 (проверка ИБ 29, УИБ29-50). В он-премис форма ответа во внешнем канале наследует `data_level` правила шлюза для этого канала, умолчание `link_only`; форма с текстом (`no_quotes`) только как `pseudonymized` настройкой компании с отметкой ОПД, по тексту с метками. Кнопки выбора проекта несут код, а не название. Расширение по умолчанию получает только метаданные, с настройкой `external_clients_content = pseudonymized` только текст с метками (`28` Р28-21, И-119): умолчание `full` для расширения отменено.

### 1.9. Сборка любого артефакта из чата и полный ежедневный контекст (A42; Дополнение 2026-10-23, A41-A45)

Слова пользователя: «встроенные агенты в чат-ботах должны уметь ответить на любой вопрос, обладая полным контекстом всего происходящего ежедневно на проекте, и должны уметь собрать любой проектный артефакт (ТЗ, ЧТЗ, детализированные постановки задач, формирование архитектуры баз данных, программирование и тестирование всех созданных разделов программного продукта, обновление документации и всех артефактов проекта сквозной двусторонней трассировкой)». Единые решения 05 §9.3, ADR-79. Согласование с 1.5-1.6, И-11, И-45 и G23: «собрать» значит запустить сборку карточкой B и получить результат, готовый к решению (ветка и MR, кандидат, черновик, запуск); «опубликовать», «согласовать», «принять», «слить», «передать в работу» остаются уровнем C, ассистент подводит к кнопке, человек нажимает на экране. ## 2. Импорт внешних файлов (A26)

### 2.1. Путь и привязка

Файл из любого канала → `office_uploads` (приём частями, sha256) → карточка B: проект (текущий; без проекта «неразобранное», `source.unsorted`), семейство, допуск, для документа «новая версия документа X» или «новый материал» (01 §2.2) → конвейер ядра (`received, parsed, chunked, indexed`). Ассистент предлагает значения по типу файла и тексту («запись созвона с заказчиком 21.10»), человек подтверждает. Повтор того же файла даёт тот же источник по sha256.

|---|---|---|---|
| Документ как версия | ветка `import/<upload_id>/<doc>` и MR «предложение заказчика» или команды (С9) | профиль версии | загрузившего |
| Документ как материал | `file:<хэш-12>` | команда; заказчику допуск «заказчик» | загрузившего |

### 2.3. Видео и аудио созвонов и демонстраций

1. Карточка спрашивает вид (`customer`, `demo`, `internal`), дату, участников; созвон без календаря (`provider=upload`) или экземпляр встречи (11 §2.2); запись `POST /calls/{id}/recording` с `upload_id`.
2. Согласие (P03): загрузивший подтверждает «участники знали о записи», отметка в `office_call_participants.consent` от его имени и в аудит; при `consent_each` без отметки загрузка не принимается (Q13-7).
3. Режим записи (11 §4.3): при `text_only` медиа удаляется сразу после распознавания (`office_call_tracks.state=deleted`), хранится расшифровка без срока (A20).
4. `SpeechRecognizer` локальный или внешний по переключателю (A24, ADR-13); проект с запретом вывоза всегда локально. Разметка «Говорящий N» уровнем 3 (11 §4.1).
5. Привязка говорящих (11 §4.5): ассистент предлагает сопоставление, подтверждает МП; `call.participant_bound`.
6. Дальше автомат 03 §3.8: `call.transcribed`, кандидаты, протокол по карточке.
7. Загруженное демо в автотест не идёт: «В автотест» только для демо во встроенном браузере с журналом (P08, 10 §14).

Резерв на H: `MediaEncoder.extract_frames` и распознавание текста кадров дают фрагменты `screen` с таймкодом; сейчас не строится.

Дополнение 2026-10-27 (проверка ИБ 29, УИБ29-55). Распознавание видео и аудио только локальное (`28` Р28-20): выбора внешнего распознавателя нет, звук наружу не уходит.

### 2.7. Лестница способов импорта (A46)

Дополнение 2026-10-23, A46: «модули импорта позволяют загружать данные в ручном и автоматическом (дельтами, по веб-хуку) режиме по API-ключам и MCP-серверам; при недоступности этих методов пользователь открывает систему во встроенном браузере и в отдельной вкладке автоматизирует выгрузку Playwright, не покидая рабочее место». Все пять ступеней ведут в один конвейер ядра (2.1): источник, карточка привязки, права загрузившего. Ступень выбирается при создании подключения («Офис → Подключения»); платформа предлагает верхнюю доступную.

| Ступень | Когда | Как | Писатель и срез |
|---|---|---|---|
| 1. Ручная загрузка | Файл есть у человека | `office_uploads` из любого канала (2.1-2.6) | `knowledge`; C, D |
| 2. API-ключ | У системы есть API и у компании ключ | Адаптер `bridge` (`describe, check, pull`), ключ в `office_credentials` (`scope` компания, проект или пользователь), `pull` по расписанию задания, курсор `office_bridge_cursor`; трекер, Google Drive (2.4), почта и календари (11) | `bridge`; G |
| 3. MCP-сервер внешней системы | Система отдаёт MCP (или у компании есть свой MCP-сервер к ней) | Адаптер `bridge` вида `mcp_client`: подключение по адресу и токену (как «Подключения» AI-Workspace, `src/connections/`), инструменты сервера перечисляются при `check`, импорт заданием зовёт инструменты чтения по описанию подключения («какой инструмент даёт список, какой элемент»); исполняется в процессе заданий под bwrap с сетью только к этому хосту; инструменты записи не вызываются | `bridge`; G |
| 4. Вебхук и дельты | Система умеет слать события или отдаёт изменения с момента | `POST /api/office/hooks/{connection_token}`, иначе опрос с курсором; дельта это новая версия источника или новый источник по ключу повтора (`external_ref`), без дублей | `bridge`; G (трекер), F (почта) |
| 5. Playwright-сценарий во встроенном браузере | API, MCP и вебхуков нет или нет ключа | Вкладка автоматизации в браузере платформы (3.12): человек открывает систему во вкладке `browser`, входит сам, записывает или описывает ассистенту выгрузку; платформа исполняет сценарий Playwright в той же сессии; результат в `office_uploads` и карточку 2.1; сценарий сохраняется и запускается по расписанию как «дельта без API» | `agents`; G |

Ступени 2-5 не дублируют друг друга по данным: ключ повтора источника один (отпечаток файла, `external_ref`, адрес), поэтому переход с 5 на 2 после появления API не создаёт второго источника. Права: подключение видит создавший и МП проекта; результаты импорта видны по карточке привязки. Входы во внешнюю систему: ступени 2-4 хранят ключи и токены в `office_credentials` (ADR-03 семейство секретов); ступень 5 хранит вход только в профиле сессии браузера (3.6, 3.12), между сессиями после юриста (Q13-12).

## 3. Браузер платформы, превью, расширение для внешних браузеров (A27, A37, A38, A40)

Переработано 2026-10-23 по A38 (слова пользователя новее 05 §7 С99 и ADR-60): «единое рабочее место со своим собственным браузером, который покрывает все потребности проектной команды для работы с проектами, проектной документацией и кодом; потребность во внешнем браузере только для сторонних программ». Собственный браузер платформы это основа рабочего места (15 §2), не отложенная часть. A40 добавляет второй равноправный путь: расширение для внешних браузеров «для универсальности платформы и сбора контекста в реальном времени, сопоставляя со всеми артефактами проекта». Оба пути работают по одному протоколу «страница → ассистент → артефакты» (3.7): один API, два клиента. A39 задаёт смысл обоих: контекст собирается онлайн по ходу работы, импорт файлов (раздел 2) это запасной путь. Единые решения по этому разделу: 05 §8; реестр: ADR-70 (ADR-60 пересмотрен).

Что остаётся внешнему браузеру пользователя: сторонние программы, которые нельзя или незачем вести через сервер: видеосвязь с камерой и микрофоном (Телемост, Толк, Zoom, Meet, 11 §3), плагин квалифицированной подписи документооборота (11 §8), личные сервисы вне белого списка компании. В этих случаях рядом с человеком работает расширение (3.9), и контекст всё равно попадает в платформу.

### 3.1. Что показывает браузер платформы

Браузер платформы это центр рабочего места (15 §2.1). Вкладка центра имеет вид (`kind`), и вид определяет, кто рисует содержимое: внутреннее содержимое рисует сама платформа (React), внешнее отдаёт серверный Chromium с трансляцией в ту же вкладку. Для человека это один браузер с адресной строкой, вкладками, историей и значком панели чата; разница видов скрыта.

| Содержимое | Вид вкладки | Кто рисует | Откуда адрес | Срез |
|---|---|---|---|---|
| Документ ядра знаний, версия, дифф, MR документа | `document` | Платформа (12 §7.1, TipTap) | Дерево 15 §2.6, ссылки `[n]` ассистента, граф 14 | B, C |
| Превью импортированного файла: PDF, таблица, Word как Markdown с оригиналом, расшифровка созвона с плеером | `preview` | Платформа (pdf.js без скриптов документа, TanStack Table, Markdown, HTML5) | `GET /sources/{id}/preview`, `/original` (2.6) | C, D |
| Страница проекта `page:<n>` (09 §2.1), требования, задачи, доска, календарь, план дня, граф, хронология, разрывы, отчёт | `screen`, `document` | Платформа; отчёт в песочнице iframe (4.5) | Маршруты 04 §7, 12 §7.3 | C-G |
| Макет (кадры Pen.dev, Figma по ссылке), интерактивный прототип | `preview` | Платформа; прототип статическим пакетом в рамке `sandbox` без сети (10 Р10-11) | `GET /mockups/{id}/preview/{frame}`, `/prototype/{path}` | D, E |
| Стенд проекта (P01): учётки ролей, «войти как роль» | `browser` | Серверный Chromium | Адрес стенда из настроек проекта, строка `source=connection` белого списка (3.4) | E |
| GitLab, GitHub: репозиторий, коммит, MR, конвейер | `browser` | Серверный Chromium | Хост подключённого репозитория (`delivery.link_repo`), ссылки из хронологии 14 §5 | E |
| Трекер компании (один в выпуске, P06): тикет по внешнему ключу | `browser` | Серверный Chromium | Хост подключения `bridge`; ключ `tracker:<system>:<key>` из ленты требования 14 §4.2 | G |
| Внешние сайты по белому списку компании: вики заказчика, документация, Google Drive и Документы | `browser` | Серверный Chromium | Белый список админа компании (3.4) | E |
| Трансляция браузера запуска агента (10 §13) | `browser` в режиме `watch` | Серверный Chromium запуска, только просмотр | Карточка запуска, журнал `browser_action` | H |

Ссылка в документе, ответе ассистента, письме или сообщении открывается так: внутренний адрес платформы во вкладке своего вида; адрес из белого списка во вкладке `browser`; адрес вне списка не открывается, вместо него карточка «адрес вне белого списка компании: запросить у администратора (одна кнопка, заявка с причиной) или открыть во внешнем браузере». Заявка админу это событие `browser_allowlist.requested`, решение одним действием в «Офис → Браузер».

### 3.2. Варианты устройства и выбор

Сравнение трёх способов дать команде «свой браузер» с расширениями магазина Chrome и доступом ассистента к содержимому любой страницы (A27). Оценки по серверу-ориентиру 00 §5 (4 ядра, 16 ГБ).

| Критерий | А. Серверный Chromium на сессию, трансляция по протоколу отладки (как Claude in Chrome, браузер Cursor) | Б. Изолированный iframe с переписывающим прокси | В. Гибрид: внутреннее рисует платформа, внешнее через серверный Chromium на узле браузера |
|---|---|---|---|
| Безопасность | Сторонний код расширений и чужие страницы живут на сервере, но в отдельном процессе под bwrap со своим сетевым пространством; данных офиса у процесса нет, только прокси и платформа | Прокси становится открытым прокси от IP студии; переписывание ломает CSP, service worker, OAuth-переадресации, встраивание запрещено `X-Frame-Options` у большинства систем; защиты от SSRF те же, что в А, но без изоляции процесса | Как А для внешнего; внутреннее не покидает процесс платформы и не проходит через Chromium, площадь атаки меньше А |
| Память на сессию | 0,5-1 ГБ (10 §13; 13 §3.3 первой редакции) за всё, включая страницы платформы | Около нуля на сервере, цена у прокси | 0,3-0,8 ГБ только у тех, кто открыл внешнюю вкладку; сессия засыпает при простое (3.3) |
| Задержка | Кадры и ввод через сервер: 80-200 мс в сети студии (доп.), для страниц платформы заметно и лишнее | Нулевая для того, что вообще открылось | Нулевая для внутреннего; 80-200 мс для внешнего, где это терпимо (трекер, репозиторий, стенд) |
| Расширения магазина Chrome | Да, в серверном профиле по белому списку админа | Нет: iframe расширения не грузит | Да, как А, только во внешних вкладках |
| Содержимое страницы ассистенту | Да, через протокол отладки: DOM, дерево доступности, выделение, снимок; по правам | Только то, что прокси смог переписать | Внутреннее: ассистент читает объект напрямую через MCP офиса (точнее любого DOM); внешнее: как А |
| Входы в сторонние системы | Куки на сервере: шифрованный профиль, вопрос юристу о хранении между сессиями | Куки у прокси: хуже, чем А | Как А, но только для внешних систем; входы в платформу куками не трогаются |
| Доступность из РФ, on-premise | Chromium из пакета установщика, магазин через зеркало или ручная загрузка CRX | Прокси работает, но половина сайтов не откроется | Как А |
| Стоимость сборки | Узел браузера, трансляция, ввод, буфер обмена, загрузки, печать | Прокси-переписчик с бесконечным хвостом исключений | Узел браузера (как А) плюс ничего: внутренние виды уже есть (15 §2) |

**Выбор: В, гибрид.** Внутреннее содержимое (документы, версии, превью, страницы, макеты, прототипы, экраны, отчёты) рисует платформа: это её собственный интерфейс, прогонять его через серверный Chromium значит удвоить память и добавить задержку без выгоды. Внешнее содержимое (стенд, GitLab и GitHub, трекер, сайты белого списка) идёт через серверный Chromium на узле браузера с трансляцией в вкладку `browser`: только так одновременно выполняются «плагины из библиотеки Google Chrome», «содержимое любой страницы ассистенту» и «не покидая платформы» (A27, A38, A41). Вариант Б отклонён: не держит расширения и ломает большинство внешних систем. Вариант А отклонён как единственный: платит памятью и задержкой за собственные страницы платформы. Решение по сравнению с 05 §7 С99: серверный Chromium для людей больше не «отложен до юриста и отдельного узла», он строится в первом выпуске на том же сервере в своём юните с пределом памяти; отдельный узел это вариант «рост» (00 §4), юристу уходит только хранение чужих входов между сессиями (3.6).

### 3.3. Узел браузера: сессия, вкладки, трансляция, ввод

Узел браузера это третий процесс платформы `ai-workspace-office-browser` (00 §5; на одном сервере рядом с вебом и процессом заданий, в варианте «рост» отдельная машина с тем же контрактом). Внутри: Chromium из образа Playwright (тот же, что у раннера `delivery`, 10 §1), по одному процессу Chromium на сессию человека под bwrap с собственным сетевым пространством, выход только через прокси узла (3.4). Контракт узла это шов `BrowserHost` (`agents`; 00 §4.1): `open_session(user, policy)`, `open_tab(session, url)`, `navigate(tab, url)`, `input(tab, event)`, `screencast(tab) -> кадры`, `page_context(tab, mode)`, `aria_snapshot(tab)`, `screenshot(tab)`, `set_file_inputs(tab, upload_ids)`, `on_download -> upload_id`, `hibernate(session)`, `restore(session)`, `close(session)`. Подделка для тестов: записанные кадры и снимки дерева доступности.

| Элемент | Решение | Доп. (P20) |
|---|---|---|
| Сессия | Одна активная на пользователя, все его внешние вкладки в ней; создаётся при первом открытии вкладки `browser`, не при входе | |

### 3.4. Сеть: белый список, SSRF, прокси

Прокси узла браузера это тот же класс прокси, что у джейла агентов (К24, 00 §6), с собственными правилами. Без прокси Chromium в сеть не выходит (сетевое пространство пустое).

| Правило | Как |
|---|---|
| Белый список | `office_browser_allowlist` (`tenancy`): строки `scope enum(company, project)`, `pattern` (хост или хост с портом, `*.` для поддоменов), `effect enum(allow, deny, no_context)`, `source enum(system, connection, admin)`, `reason`, `added_by`. `no_context` значит «открыть можно, ассистенту не читать» (вход, банк, личная почта) |
| Системные строки | Публичный адрес платформы; стенд проекта из настроек проекта (P01); хост репозитория из `delivery.link_repo`; хост трекера из подключения `bridge`; хосты Google Drive при подключённом `google_drive`. Пишутся `source=connection` при создании подключения, снимаются при его удалении |
| Проверка | До навигации (адресная строка, ссылка, переадресация, под-ресурсы страницы): прокси отвечает 403 своей страницей «вне белого списка» с кнопкой заявки; событие `browser.blocked` |
| SSRF | Прокси резолвит имя сам и прибивает адрес на время соединения (защита от перепривязки DNS); частные диапазоны (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, fc00::/7, ::1), адреса метаданных облака и порты самой платформы запрещены, кроме явных строк стенда с `effect=allow` и признаком `private_ok`, которые ставит админ компании с подтверждением; `file:`, `chrome:`, `devtools:` закрыты флагами Chromium |
| Выход от IP студии | Внешние системы видят адрес сервера платформы, не сотрудника: это заметно для систем с привязкой входа к IP; пишется в справку подключения; по желанию компании прокси выходит через её корпоративный шлюз (настройка `browser.egress_proxy`) |
| Расширения в сети | Запросы расширений идут через тот же прокси и белый список: расширение не может отправить данные на свой сервер, пока админ не добавил его хост явно (3.5) |
| Журнал | Прокси пишет хост, метод, статус, байты в журнал узла (ротация 14 дней, не данные проекта); содержимое не пишет |

Дополнение 2026-10-27 (проверка ИБ 29, УИБ29-69). (1) Прокси узла браузера выходит наружу только через шлюз `core` с назначением `browser` (`28` §7.1); настройка `browser.egress_proxy` действует только за шлюзом. (2) `private_ok` ставится только на точный хост и порт без шаблона `*.` и не выдаётся автоматически системной строкой подключения: внутренний трекер или GitLab компании добавляет АдмК с подтверждением. (3) Инфраструктура контура закрыта при любом правиле: узел моделей, шлюз и SMTP-ретранслятор, порты платформы, хранилище копий, админ-API Caddy (И-137). (4) Навигация только по `http` и `https`.

### 3.5. Расширения магазина Chrome

Расширения грузятся в серверный профиль Chromium (`--load-extension`, `--disable-extensions-except`; в `headless=new` поддерживаются, проверить версию при сборке образа). Сам магазин Chrome внутри серверного браузера не работает (нет входа Google и потока «установить»), поэтому допуск и загрузка идут через платформу.

| Шаг | Как |
|---|---|
| Каталог компании | `office_browser_extensions` (`tenancy`): `extension_id` (идентификатор магазина, 32 символа), `name`, `version`, `crx_sha256`, `source enum(store, upload)`, `permissions json`, `host_permissions json`, `state enum(pending, approved, blocked, retired)`, `approved_by`, `approved_at`, `enabled_for enum(all, roles, users)`, `targets json` |
| Заявка | Любой участник вставляет ссылку магазина в «Браузер → Расширения»; платформа тянет CRX с адреса обновлений магазина (`clients2.google.com/service/update2/crx` через прокси сервера, не узла браузера), проверяет подпись CRX3 и соответствие идентификатора ключу, читает `manifest.json`, показывает админу разрешения и хосты; при недоступности адреса из РФ админ загружает CRX руками (`source=upload`) с той же проверкой |
| Допуск | Админ компании переводит в `approved` с версией; обновление версии это новая строка и новый допуск, автообновления выключены (`--extensions-update-frequency` большой, адрес обновлений через прокси закрыт); расширения с `<all_urls>` и `webRequest` помечаются предупреждением, но не запрещаются |
| Включение | Пользователь включает одобренные у себя (`office_company_users.settings.browser.extensions[]`); при открытии сессии грузятся только включённые; событие `browser_extension.loaded` в журнал сессии |
| Данные расширения | Живут в профиле сессии (3.6); расширению видны только страницы, которые видит человек; сеть по 3.4 |
| Ограничения | Не работают: расширения с входом через аккаунт Google (`chrome.identity`), нативные хосты (`nativeMessaging`), расширения, требующие заголовок окна Chrome (темы, панели инструментов), DRM; боковые панели расширений (`chrome.sidePanel`) не показываются, панель чата платформы занимает это место; всплывающие окна расширений рисуются внутри кадра как отдельная вкладка |
| Срез | G (вместе с отчётами и расширением для внешних браузеров); схема и столбец `extensions` сессии кладутся в E |

Расширения для внешнего браузера пользователя (его Chrome) платформу не касаются: там он ставит что хочет, а контекст платформе отдаёт расширение «Ассистент офиса» (3.9).

Дополнение 2026-10-27 (проверка ИБ 29, УИБ29-85). Прокси различает инициатора запроса `chrome-extension://<id>` и пускает расширение только на хосты его одобренных `host_permissions`. В он-премис по умолчанию не допускаются расширения с `<all_urls>`, `webRequest`, `debugger`, `cookies`; на хостах `no_context` и `private_ok` расширения выключены.

### 3.7. Единый протокол «страница → ассистент → артефакты»

Один протокол для двух клиентов: вкладки `browser` платформы (контекст извлекает узел через протокол отладки) и расширения во внешнем браузере (контекст извлекает расширение на стороне человека, 3.9). Внутренние виды (`document`, `preview`, `screen`) в протокол не входят: ассистент читает сам объект через MCP офиса (1.4), это точнее любого текста со страницы.

| Шаг | Что происходит |
|---|---|
| 1. Захват | Клиент собирает `page_context`: адрес (запрос без параметров входа), заголовок, выделение, основной текст (Readability, только видимое, до 30 тыс. символов), при запросе снимок дерева доступности и снимок видимой части. Режимы: `manual` (кнопка, «Спросить о странице», «Спросить о выделенном», пункт контекстного меню); `match` (на каждой навигации уходят только адрес и заголовок, текст не уходит); `full` (адрес, заголовок и текст на каждой навигации, только на хостах `effect=allow`). Режим выбирает пользователь в настройках браузера, умолчание `manual`; админ может запретить `full` компанией. На хостах `no_context` захват не работает, клиент показывает причину |
| 2. Политика | `tenancy.browser_policy(user, url)`: белый список и `no_context`, клетки матрицы `browser/use`, `assistant/page_context`; запрещённое не покидает клиент (расширение проверяет список локально по кэшу `GET /browser/policy`, узел проверяет сам) |
| 3. Сопоставление | `insight.match_artifacts(page_context)` в правах человека: по адресу (ключ тикета трекера из `office_bridge_links`, путь репозитория, номер MR и sha коммита из `delivery`, ссылка на документ или источник платформы, адрес стенда и экран по карте «экран → API»), по тексту (ключи требований и задач `ABC-R-12`, `ABC-12` в тексте; `knowledge.search` по заголовку и выделению с порогом, срез C) → список узлов графа артефактов 14 §3 с `confidence` и ребром-кандидатом. Ответ без модели, до 1 с (доп.); с моделью только при явном вопросе ассистенту |
| 4. Показ | Панель чата у вкладки (или боковая панель расширения) показывает «На этой странице: задача ABC-12 (в работе), требование R-5 (принято, версия 6), MR !42 (слит)», каждое ведёт на объект; кнопки «Спросить», «Импортировать страницу», «Привязать к …» |
| 5. Вопрос | `POST /assistant/threads/{tid}/messages` с `page_context_id`: ход ассистента (1.2) получает контекст в рамке «внешний материал» (02 §10), совпадения как подсказку инструментам; карточки B после такого хода помечены (1.5) |
| 6. Запись в ядро | «Импортировать страницу»: источник `web:<хэш адреса>` вне Git (01 §2.2), карточка B по правам `assistant.import_*`, дальше конвейер ядра; совпадения 3 становятся предложенными рёбрами `references` к узлам (сторона `human`, способ `manual`, 14 §3.4) и подтверждаются человеком одним нажатием. «Привязать к требованию или задаче» без импорта: улика `office_evidence` из источника `web:*` операцией `cycle` (карточка B). Экран созвона: страница как материал к созвону (`call:<id>` ← `web:*`) |
| 7. Хранение | `page_context` эфемерен: 30 минут в памяти веб-процесса, в базе только то, что человек вложил в сообщение (`office_assistant_messages.page_context`) или импортировал. В режимах `match` и `full` ничего не пишется, кроме события `page_context.captured` без текста (адрес хэшем) для аудита по согласию пользователя (Q13-5) |

Сопоставление в реальном времени (A40) это режимы `match` и `full`: человек ходит по трекеру, репозиторию или вики заказчика, а панель сама показывает связанные артефакты и предлагает записать увиденное; ничего не записывается без нажатия. Инъекция со страницы может только предложить карточку, не исполнить (02 §10, 1.5). Действия ассистента на внешней странице (нажать, заполнить) в первом выпуске не строятся: отложено до пилота P20 с причиной «инъекция на странице под входом человека управляла бы сторонней системой; нужен файрвол действий по образцу 02 §4.3 и замер пользы»; место: уровень B в `office_assistant_actions` с `op=browser_action`.

### 3.8. Агент и человек: один движок, два хоста; что остаётся от P23

| | Браузер запуска агента (02 §9, 10 §1) | Браузер человека (3.3) |
|---|---|---|
| Движок | Chromium и Playwright из одного образа установщика; один формат журнала `browser_action`; один клиент трансляции в вкладке `browser` | то же |
| Хост | Внутри джейла запуска агента, `BrowserRunner` (`delivery`) для раннера и агентов | Узел браузера `BrowserHost` (`agents`) |
| Профиль | Новый на запуск, удаляется после (C34) | На сессию человека, шифруется при сне (3.6) |
| Сеть | Только стенд проекта (P01, К24) | Белый список компании и проекта (3.4) |
| Расширения | Нет | По допуску админа (3.5) |
| Входы | `login_as(role)` инструментом | Свои и «войти как роль» на стенде |
| Журнал | `office_agent_run_log.kind=browser_action` | `office_browser_events`; в режиме записи демо тот же формат `browser_action` в источник `demo:browser-<session>` (01 §2.2) |
| Кто смотрит | Команда в режиме `watch` (H, 10 §13) | Только владелец |

Хост запуска агента не переносится на узел браузера намеренно: браузер агента должен жить в сетевом пространстве его джейла, где кроме стенда ничего нет (P23, К24), а узел браузера видит белый список компании. Два хоста, один движок.

**P23 после A38.** Остаётся: браузер запуска агента ходит только на стенд проекта с изолированным профилем на запуск; агентам внешние адреса не открываются (H2 отложено, причина: инъекция с внешней страницы в агента, который пишет в ветки и черновики; нужен белый список для агентов с аудитом и ответ юриста о чтении сторонних сайтов агентом, Q13-8). Снято словами A27 и A38: «браузер только для агента». Шаги 10 §13: H1 (человек ведёт браузер стенда, демо с журналом) входит в первый выпуск как вкладка `browser` со стендом в белом списке и кнопкой «записывать демо» (журнал в формате `browser_action`, источник `demo:browser-<session>`); кнопка «В автотест» по-прежнему отложена словом пользователя (P08, D06), её условие «демо во встроенном браузере с журналом» теперь выполнимо; H3 (профиль пользователя с входами) входит в первый выпуск в границах 3.6, между сессиями входы хранятся только после ответа юриста.

Дополнение 2026-10-27 (проверка ИБ 29, УИБ29-63). В режиме записи демо поля пароля и текст `login_as` маскируются в журнале действий; журнал демо проходит `pseudonymize` (И-107). `login_as` идёт в эфемерном контексте, сверяет источник главного фрейма со стендом в момент вставки (без вставки после переадресации и во вложенные фреймы); куки стенда стираются по `member.removed` и `member.role_changed`.

### 3.9. Расширение для внешних браузеров (A40)

Расширение «Ассистент офиса» это второй клиент протокола 3.7, равноправный с браузером платформы: для универсальности (сторонние программы, браузер по привычке, чужой компьютер) и сбора контекста в реальном времени с любой страницы с сопоставлением с артефактами проекта.

| Элемент | Решение |
|---|---|
| Браузеры | Chrome и Chromium-семейство (Яндекс Браузер, Edge, Opera, Brave): Manifest V3, `chrome.sidePanel`, магазин Chrome; Firefox: тот же код, `sidebar_action`, подпись и публикация на AMO (с пометкой: проверить `sidePanel` против `sidebar_action` и `scripting` в сборке); Safari: сборка через Safari Web Extension (Xcode, аккаунт Apple Developer), без боковой панели, только всплывающее окно (с пометкой: по возможности, срез H). Один исходник, три сборки |
| Интерфейс | Боковая панель с теми же компонентами ассистента, что в каркасе (15 §2.9: `Chat.tsx`, карточки, мини-граф); без панели всплывающее окно; пункт контекстного меню «Спросить ассистента о выделенном» |
| Вход | Страница платформы выдаёт токен клиента `extension` (`office_api_tokens`, область «ассистент», доступ 1 час, обновление 30 дней, `chrome.storage.session`; отзыв в профиле сразу; 02 §7) |

### 3.12. Вкладка автоматизации: сценарии импорта Playwright (A46)

Пятая ступень лестницы 2.7. Довод в пользу серверного Chromium с протоколом отладки (3.2): сценарий исполняется в той же сессии и том же профиле, где человек только что вошёл в систему; расширению во внешнем браузере это недоступно без `<all_urls>` и `debugger`.

| Элемент | Решение |
|---|---|
| Вход | Человек открывает систему (трекер без API, облачный диск, старый портал заказчика) во вкладке `browser` (хост из белого списка, при необходимости заявка 3.1), входит сам; кнопка «Автоматизировать выгрузку» открывает вкладку автоматизации рядом с той же сессией |
| Запись | «Записать»: действия человека пишутся в формате `browser_action` (навигация, клики и ввод по локаторам роли и имени из дерева доступности, выбор файла, загрузка) в черновик сценария; секреты из полей пароля не пишутся (маска), вход считается сделанным до записи |
| Описание | «Описать ассистенту»: человек говорит, что выгрузить («все тикеты проекта X за месяц в CSV», «список файлов папки с датами»); ассистент одношаговым вызовом класса `browser_check` (10 Р10-01) пишет черновик шагов по снимку дерева доступности текущей страницы; модель сценарий не исполняет, только пишет и чинит локатор при поломке |
| Формат | Шаги формата сценария 10 §2 (локатор по роли и имени, `fixtures` для параметров, `assert_visible`, `download`, `read_table`, `read_text`); параметры даты и периода подставляет код при запуске («с прошлого запуска» = курсор) |

## 4. Отчёты, экспорт, ролевая матрица (A29, A30, A31)

### 4.1. Место в модулях

| Что | Модуль |
|---|---|
| Агент `report_builder`, ход построения, журнал | `agents` (многошаговая работа, выше домена) |
| Каталог наборов данных, компилятор, рендер HTML, каталог отчётов и права | `insight` (владелец аналитики; компилятор уже здесь по 12 §4.2) |
| PDF, DOCX, XLSX, статичные графики | `knowledge`, шов `ExportRenderer` (экспорт версий уже у `knowledge`; прецедент `MediaEncoder`, ADR-44). PDF печатает безголовый Chromium в процессе заданий под bwrap без сети своим вызовом, не через `BrowserRunner`: `delivery` выше `knowledge` (05 §7 С77) |
| Матрица прав, проверка раздела | `tenancy` (`can`) |

`insight` читает наборы `cycle` и `knowledge`. Рёбра чтения `insight → cycle` и `insight → knowledge` записаны в 00 §3.3 (05 §7 С78): вызов вниз, циклов нет; запись вниз у `insight` по-прежнему только `trigger_risk`, `observe_risk`.

### 4.2. Построение

1. Запрос с экрана «Отчёты» или из ассистента (`report_draft`, уровень A); проверка `reports.create`.
2. `report_builder` (класс `report`) получает каталог наборов в правах автора: невидимого автору нет в каталоге, модель о нём не знает.
3. Ряды через `dataset_query` (до 2 000 ячеек на ответ), фрагменты через `search` и `ask`. Модель видит только видимое автору; отличие от 12 §4.2 намеренное: тексту нужны значения.
4. Агент пишет спецификацию (4.3); SQL, HTML и JavaScript модель не пишет.
5. `insight.compile_report(spec, actor)`: схема, белый список, ссылки на наборы, область прав, пределы; одна попытка исправления по ошибке, затем отказ с объяснением.
6. `insight.render_report(revision)`: серверный шаблон с автоэкранированием; числа текста подставляет код из фактов; `[n]` сверяет `verify_quote`; ревизия получает `data_classes`.
7. Черновик видит только автор; «Сохранить» ведёт в каталог (4.5).

Ход это запуск `office_agent_runs`; около $0,40 за отчёт (доп.: 60 тыс. токенов входа, 8 тыс. выхода сильной моделью), потолок резерва 150 тыс., таймаут 10 минут.

1. Права при сохранении: роли, люди, «все с доступом к разделу». Получатель должен видеть каждый класс ревизии (`tenancy.scope` и матрица), иначе строка неактивна с причиной (A22) и кнопкой «пересобрать без бюджета».

Порядок проверки `tenancy.can(actor, section, action, scope)`:

1. `users.is_admin` (администратор платформы, ADR-23): разрешено; действие в контенте проекта пишется `admin_as_role`.
2. Закреплённая клетка: значение из слов пользователя.
3. Иначе клетка текущей ревизии; роли актора из `office_memberships` или область наблюдателя (`portfolio_scope`); разрешает любая роль, кроме закреплённого запрета.
4. Дальше операция домена (03 §4.1, запреты агентам) и профиль видимости до ранжирования. Профили (`office_visibility_profiles`) решают, что роль видит в содержимом; матрица решает, какие разделы и действия доступны; отчёт и ассистент профиль не обходят.
