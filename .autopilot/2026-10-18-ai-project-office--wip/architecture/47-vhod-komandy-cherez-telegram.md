# 47. Вход проектной команды через Telegram

Документ для разработчиков. Дополняет `11` §6.2 и `43`. Слово пользователя 2026-10-31: команда входит и паролем, и через Telegram, Telegram привязан к учётке и нужен для уведомлений.

## 1. Зачем

Белый список `ALLOWED_USER_IDS` даёт все проекты, подписку владельца и Claude без confine и джейла (`43`, У43-02). Команду в него добавлять нельзя. Нужен вход через Telegram без этих прав.

## 2. Модель

Один человек, одна локальная учётка, два способа входа. Telegram открывает ту же учётку с теми же правами, что и пароль: сессия несёт локальный id и claim `tv`. Поэтому `is_account_active`, `resolve_project_access` и `routes_ws` не менялись.

## 3. Решения

| № | Решение | Почему |
|---|---|---|
| Р47-01 | Активная привязка `office_channel_bindings` открывает вход | Новое право сверх `11` §6.2: там привязка только для уведомлений |
| Р47-02 | Таблица и привязка сделаны раньше среза F, конвейер уведомлений остаётся в срезе F | Вход нужен сейчас |
| Р47-03 | `access.channel_bound` пишется в журнал, почтовый дубль придёт со срезом F | Почты в коде нет |
| Р47-04 | Один бот на вход и уведомления: в срезе F в `office_credentials` кладётся токен этого же бота (уточняет УИБ29-74, `18`) | Иначе `/start` окажется не у того бота |
| Р47-05 | Учётка с `is_admin` и выключенная через Telegram не входят. Повышение до админа гасит сессии (`token_version`) | Telegram не заменяет пароль админа |
| Р47-06 | Привязка только у локальных учёток, подтверждение текущим паролем с лимитером | Украденная сессия не закрепит чужой Telegram (усиливает УИБ29-32) |
| Р47-07 | Один Telegram на учётку и наоборот, частичные UNIQUE при `state='active'` | `11` §6.2 |
| Р47-08 | Новые локальные id выше 2^52 | Telegram обещает id до 52 бит. Иначе локальный id мог совпасть с id из белого списка. Старые учётки не меняются, вход через Telegram им закрыт при совпадении |
| Р47-09 | Отвязка активной привязки гасит все сессии. Сброс пароля и удаление учётки снимают привязку | JWT живёт дни; вор пароля не вернётся через свой Telegram |
| Р47-10 | Строка `users` пишется только для белого списка | Посторонний с верной подписью не занимает логин и не двигает счётчик id |

## 4. Поток

1. Настройки, кнопка: `POST /api/me/telegram/start` даёт `t.me/<бот>?start=bind_<код>`. Код одноразовый, 10 минут, в базе только хэш.
2. Бот (`cmd_start_bind`, личный чат, только текст) запоминает аккаунт. Неверный код получает молчание.
3. Веб показывает имя и id аккаунта. `POST /api/me/telegram/confirm` с паролем делает привязку активной.
4. Вход: виджет `POST /api/auth/telegram` или ссылка `/weblogin` через `POST /api/auth/magic-link`. Правило одно: `resolve_team_account` (`src/web/telegram_team.py`).

Вне белого списка бот понимает только `/start bind_<код>` и точное `/weblogin` в личном чате (`AuthMiddleware`). Claude из бота есть только у белого списка.

`GET /api/auth/config` отдаёт странице входа имя бота: `VITE_BOT_USERNAME` установщик не задавал, виджета на проде могло не быть.

## 5. Шаги оператора

В BotFather: `/setdomain` на домен панели и каждый участник в Allowed users.

## 6. Границы

- Второй фактор (`28` §7.3, таск 138): точка выпуска одна, `_start_local_session` в `src/web/routes_auth.py`. Таск 138 встраивает проверку туда и закрывает оба пути.
- Рассылка событий платформы не сделана: нужен конвейер `11` §6.1.
- Участник, приглашённый раньше по telegram id без локальной учётки, не входит через Telegram: админ заводит ему локальную учётку.
- Внешних ключей между `users` и `office_channel_bindings` нет (`43`, Б43): отзыв при удалении стоит в роуте `routes_admin.py`.
