## Сокращения и термины

- **ПМО** проектный офис (PMO, project management office). **РПО** руководитель проектного офиса (`pmo_head`). Остальные роли как в `27`: МП, БА, СА, Арх, Раз, Тест, Тим, ТЛ, Наб п (наблюдатель проекта), Наб о/к (наблюдатель подразделения или компании, `portfolio_scope`), Пр и Подп (представитель и подписант заказчика), АдмК (администратор компании), АдмП (администратор платформы), ОПД (ответственный за обработку персональных данных, флаг учётки, `28` Р28-08), Аг (агент).
- **Пространство компании** служебное пространство документов проектного офиса, не связанное с проектом заказчика (A80, `09` В-1).
- **Профиль ПМО** машинная часть методологии: тип офиса, обязательность наборов, режим ворот, шаги РПО, критерии приоритизации. **Профиль политики ИИ** машинная часть регламента ИИ: разрешённые классы задач, модели, данные, облако, пороги проверок.
- **Портфель** все проекты области (подразделение или компания). **Весовая оценка** приоритет проекта как сумма оценок по критериям, умноженных на веса критериев. **Цикл портфеля** один пересмотр портфеля: оценка, сценарии, решение комитета. **Портфельный комитет** руководство, которое решает, какие проекты начинать, продолжать, приостанавливать.
- **Веха** контрольная точка проекта: элемент ИСР вида `milestone` (крупный тип), этап договора (`contracts`) или служебная веха набора у маленького типа (§6.8). ИСР иерархическая структура работ. ЗС заинтересованные стороны.
- **Описание работ** (SOW, statement of work) документ «что должен сделать поставщик». **Запрос предложений** (RFP, request for proposal) документ, который рассылают поставщикам, чтобы получить предложения.
- **Набор предвзятости** синтетические пары входов, которые отличаются только признаком, не влияющим на суть (имя, пол, возраст, сторона), для проверки, меняет ли признак вывод модели. **Ц-В1** замер качества локальной модели до выпуска (`28` §3.5).
- **Порог k** минимальное число людей в ячейке агрегата, ниже которого ячейка не показывается (`26`, И-95, И-100).
- Классы данных как в `13` §4.5, `26` §2.1, `27`: `team`, `customer`, `budget` (деньги, только клетка `plan.budget/view`, A22), `internal_text`, `code`, `usage`, `personal`, `showcase`, `management_chat`.
- Числа без источника помечены «калибровка, не цель». Внешние модели, методики и продукты без проверки помечены «не проверено». Уровни источника PMBOK (ОФ, ВТ, НП) как в `30` §0.

| Аудитории документов | Поле версии `space_audience enum(company, management)`: `company` читают все сотрудники стороны исполнителя (клетка `pmo/view_company_docs`); `management` читают РПО и Наб о/к (`pmo/view_management_docs`; сверка 32, У32-19: АдмК не руководство, клетка у него «-», админ может открыть). Аудитория пишется меткой `audience:company` или `audience:management` в `scope_tags` фрагментов и векторов версии (И-86), поиск фильтрует по клеткам читателя (сверка 32, У32-02) |
| Правка | Ветки и MR как у документов проекта; автор с клеткой `pmo/edit_docs`; ревью по пунктам для видов с `review_policy = manual_items` (`25` §6). Сверка 32 (С32-22): у `policy:ai_use` разделы закреплены за ролями (АдмК: модели и облако; ОПД: данные; РПО: остальное); слияние MR, где автор правил чужой раздел, отклоняется 422 `section_not_permitted` по якорям разделов |
| Маршрут | Вид маршрута `company_doc` (таск 13): автор, затем согласование РПО (если автор не РПО), для `policy:ai_use` согласование АдмК и ОПД, последний шаг утверждение наблюдателем области компании (`pmo/approve_docs`). Утверждающий не автор и не последний правивший (И-123); в компании, где один человек несёт несколько флагов, пишется запись «один человек в двух ролях» (как `28` Р28-08) |
| Поиск | `knowledge.search` внутри пространства компании для его редакторов и запусков его области; поиск из проекта в пространство компании и обратно не идёт (И-89) |
| В проекты | `knowledge.company_doc(company, kind)` отдаёт последнюю принятую версию `pmo:methodology` и `policy:ai_use` аудитории `company`; сборщик конституции агента (`02` §4.2) кладёт выжимку, собранную кодом из профиля (тип офиса, режим ворот, обязательные пункты набора, ключ и номер версии; до 150 токенов, калибровка, не цель: бюджет конституции 800 токенов, `01` §7.5), а инструмент ассистента и агентов `company_docs` (таск 70) отдаёт полный текст блоком «материал источника» с версией. Сверка 32 (У32-01, С32-07): блок и инструмент работают только в запусках, чья аудитория вывода содержит класс `team` (`internal`, `management`), и в облачных запусках только при `team` в классах включения облака |
| Проверка слияния | Детектор валют, словарь заказчиков компании, ключи `REQ`, коды проектов (как `26` И-94): 422 `company_space_leak` с найденными местами |

### 3.2. Документ методологии компании

**Вид** `pmo:methodology`, аудитория `company`, `data_class = team`, `review_policy = manual_items`, `refresh_policy = notify`, маршрут `company_doc`. Шаблон поставляемого набора; компания правит свою копию.

| Раздел | Кто пишет | Откуда собирается |
|---|---|---|
| 1. Назначение офиса и каталог услуг (устав ПМО) | РПО | текст; агент предлагает черновик по пробелам (сессия проработки, `23`) |
| 2. Принципы и мерило (PMBOK 8: 6 принципов, 7 доменов, 5 фокусных областей; ссылка на `30`) | РПО | текст плюс таблица «принцип → механизм платформы» из `30` §5.1 |
| 3. Тип и модель офиса | код | профиль ПМО: тип, область (компания, подразделения), флаги поведения §3.3 |
| 4. Типы проектов, методики и наборы артефактов | код | `office_artifact_presets` компании (`21` §4): состав по фокусным областям, отметка `required` у обязательных пунктов |
| 5. Вехи и критерии выхода | код | шаблоны `gate:<веха>` компании (§6.8): пункты, требуемые статусы, кто подписывает акт |
| 6. Адаптация (что проект может менять) | код плюс текст | флаг `preset_obligation` профиля: что проект меняет сам, что с причиной, что с согласия РПО |
| 7. Роли и ответственность офиса | РПО | 12 ролей `03` §2.2, клетки ПМО §8.5, RACI офиса |
| 8. Портфель: критерии и метод приоритизации, цикл, комитет | код плюс текст | `portfolio_criteria` профиля (веса, шкалы), периодичность цикла |
| 9. Отчётность руководству | код | подписки О4, О10, О-ПМО-1 по типу (§3.3) |
| 10. Управление изменениями и конфигурацией | код | автомат CR (`09` §4.3), маршрут базы, метки `accepted`, комплекты (`22` §4.4) |
| 11. Использование ИИ | ссылка | версия `policy:ai_use` |
| 12. Совершенствование: зрелость и дорожная карта | ссылка | последняя версия `pmo:maturity` (название уровней без показателей по проектам) |

Входы версии (`22` §4.1, новые виды входа в таске 96): `pmo_profile` (ревизия профиля), `document_version` (версии шаблонов наборов и `policy:ai_use`). Разделы, помеченные «код», агент не пишет: их собирает `draft_artifact` из настроек; правка руками такого раздела отклоняется ревью пунктом `generated_section` с подсказкой «измените профиль».

**Связь с наборами и адаптацией `21` §4.** Набор остаётся записью каталога; профиль добавляет к пункту набора `required bool` и правило отклонения проекта от набора: `suggest` (проект меняет набор сам), `required` (отклонение пишется с причиной в `office_projects.settings.preset_deviations [{template_kind, reason, by, at}]` и видно в О-ПМО-1), `required_locked` (отклонение и правка копии шаблона только с согласия РПО шагом маршрута). Сверка 32 (С32-19): писатель поля `project` операцией `project.record_preset_deviation(project, template_kind, reason)`; её зовёт `ui` (режим `required`) или `cycle` после шага РПО (режим `required_locked`); читают `cycle` и `insight`; `knowledge` ниже `project` и читает только флаги профиля у `tenancy`.

**Активация.** Принятие версии методологии (`version.accepted`) ведёт `cycle`: он зовёт `tenancy.activate_pmo_profile(company, revision)` для ревизии из входов принятой версии. Без принятой методологии действует профиль по умолчанию `supportive` (поведение платформы до этого раздела).

### 3.3. Тип проектного офиса как настройка

Источники типов: «поддерживающий, контролирующий, директивный» по материалам PMI вне PMBOK (ОФ, `30` §6.1); корпоративный, подразделения, agile-ПМО, офис поставки ценности, центр компетенций по вторичным источникам (ВТ). Тип не выбирает «правильную» модель: PMBOK 8 X2.4 говорит, что рабочие офисы обычно смешанные (ВТ). Поэтому тип это пресет флагов, а `mixed` даёт флаги по одному.

`office_pmo_profiles.kind enum(supportive, controlling, directive, mixed)`, `scope enum(company, departments)`; при `departments` каждое подразделение получает свой тип строкой `department_overrides` (ПМО подразделения), проект берёт тип своего подразделения. Сверка 32 (С32-25): флаг `pmo_head` только уровня компании (`29`, `tenancy.set_company_role_flag`); ПМО подразделения ведёт наблюдатель подразделения в своей области клетками `portfolio/*` с «о» (подцели, оценки, сценарии, ёмкость области); второго `pmo_head` с видом на всю компанию ради подразделения не заводят.

| Поведение (флаг профиля) | Поддерживающий | Контролирующий | Директивный |
|---|---|---|---|
| Наборы артефактов (`preset_obligation`) | `suggest`: набор предлагается, проект меняет сам | `required`: обязательные пункты набора; отклонение с причиной | `required_locked`: отклонение и правка копии шаблона с согласия РПО |
| Критерии выхода на вехе (`gate_mode`) | `advisory`: акт вехи можно оформить с красными пунктами, причина МП | `controlled`: акт только при зелёных пунктах или «принято с отклонением», отклонение подтверждает РПО | `directive`: шаг РПО в маршруте акта вехи обязателен |
| Страж цепочки, умолчание режима (`guard_default`, `14` §6) | `warn` | `gate` для видов, которые уходят заказчику | `gate` для всех видов с политикой ревью |
| Шаг РПО в маршрутах планов (`rpo_step_plans`) | нет | `plan:management`, `plan:finance` | все `plan:*` |
| Старт проекта (`start_requires_decision`) | МП переводит в `active` | как поддерживающий; портфель показывает «без решения комитета» | `active` только после `project.approve_start` по решению комитета `approve_start` (И-144); переход `draft → active` по `POST /projects/{pid}/status` без него даёт 409 `start_decision_required`. Сверка 32 (С32-03): флаг доступен для активации только после таска 149 (G2), до того предпросмотр пишет «появится после среза G2» и флаг не включается |
| Назначение МП (`pm_assignment`) | АдмК или МП (как сейчас, таск 08) | как сейчас | РПО: черновик ревизии матрицы открывает роли РПО клетку `project/assign_pm`; назначающий не назначает себя (409 `same_person`), назначение уведомляет АдмК и прежнего МП (сверка 32, У32-03) |
| Отчёт о соответствии методологии (О-ПМО-1, таск 115) | нет | подписка ежемесячно (калибровка, не цель) | подписка еженедельно (калибровка, не цель) |
| Отчёт руководству О4 | по подписке МП | подписка обязательна, ежемесячно | подписка обязательна, еженедельно |

Правила:
- Профиль меняется только новой ревизией (`draft → proposed → active`); предпросмотр `POST /company/pmo-profile/preview` показывает, какие проекты и маршруты затронет, какие пункты ворот станут красными, какой черновик матрицы появится.
- Открытые маршруты, акты и ревью сохраняют свои шаги; новое правило действует с новых маршрутов и вех (нет задним числом).
- Флаги читают нижние модули через `tenancy.pmo_profile(company, department?)`: `knowledge` (обязательность пункта набора), `cycle` (`check_gate`, режим стража, шаги маршрута), `project` (`approve_start`), `insight` (подписки и критерии).
- Сверка 32 (У32-17). Шаг РПО в маршрутах планов и актов вехи даёт РПО чтение только версии на этом шаге (как последний шаг маршрута базы, `09` §6.4) с записью в аудит, а не доступ к остальному проекту; подписки О4 и О-ПМО-1 до таска 115 (G3) пишут «данных пока нет».
- Сверка 32 (У32-03). Ревизия матрицы из черновика профиля, которая расширяет права роли самого применяющего (например АдмК, он же РПО) или роли `pmo_head`, применяется только после подтверждения второй учёткой с другим вторым фактором (И-123); в компании с одной учёткой исполнителя с флагом АдмК пишется отметка «один человек в двух ролях».

### 3.4. Оценка зрелости

**Модель платформы** (своя; похожие шкалы из пяти уровней есть у известных моделей зрелости организаций, например CMMI, OPM3, P3M3, их тексты и критерии не использовались, не проверено).

Уровни: 1 «по случаю» (делается, когда кто-то вспомнил); 2 «повторяемо» (делается в большинстве проектов одинаково); 3 «по правилу» (описано в методологии и обязательно); 4 «измеряется» (есть показатель и порог, отклонения видны); 5 «улучшается» (по показателям меняют методологию и наборы).

| Измерение | Вопросы анкеты (пример) | Показатели из платформы |
|---|---|---|
| И1 Руководство и методология | Методология утверждена и известна; адаптация описана | Есть принятая `pmo:methodology` не старше года; доля проектов с отклонениями набора без причины |
| И2 Портфель и стратегия | Проекты связаны с целями; приоритет пересматривается по циклу | Доля проектов с подтверждённой связью с целью; циклы портфеля за год |
| И3 Планирование и контроль сроков и финансов | База утверждается до исполнения; отклонения разбираются | Доля крупных проектов с принятой базой; доля вех, пройденных в пределах порога отклонения (калибровка, не цель) |
| И4 Риски и изменения | Реестр рисков живой; изменения идут запросами | Доля проектов со снимком `register:risks` за 30 дней; доля CR с оценкой влияния |
| И5 ЗС и коммуникации | Есть план вовлечения и коммуникаций | Доля проектов с принятыми `plan:stakeholder_engagement` и `plan:communications`; своевременность статусных отчётов |
| И6 Ресурсы и команда | Ёмкость ролей известна; ретро проводятся | Есть ёмкость ролей на текущий квартал; доля спринтов с ретро |
| И7 Знания и совершенствование | Уроки становятся решениями библиотеки | Доля закрытых проектов с уроками; карточки библиотеки за год |
| И8 Ценность и выгоды | Выгоды измеряются после сдачи | Доля проектов с `plan:benefits` и хотя бы одним измерением |
| И9 ИИ в управлении проектами | Политика ИИ утверждена; результаты ИИ проверяются | Есть принятая `policy:ai_use` в сроке; доля классов с зелёной проверкой предвзятости; доля пунктов ИИ, прошедших ревью по пунктам |

Ход:
1. РПО открывает кампанию (`pmo/maturity_run`): респонденты по ролям (умолчание РПО, все МП активных проектов, Наб о/к, Тим и ТЛ по выбору), срок 10 рабочих дней (калибровка, не цель). Периодичность ежеквартально (калибровка, не цель).
2. Респондент отвечает по шкале 1-5 на 3-4 утверждения измерения (калибровка, не цель); ответ хранится с псевдонимом.
3. Код считает показатели (`insight.maturity_indicators`) только агрегатами по проектам области; порог перевода показателя в уровень задан в модели (калибровка, не цель).
4. Итог по измерению две колонки: «самооценка» (медиана ответов, только от порога k = 3, калибровка, не цель, иначе «мало ответов») и «по данным» (уровень по показателям); разрыв больше одного уровня подсвечен. Общий итог медианой измерений, тоже двумя колонками. Сверка 32: самооценка без разбивки по ролям и без сравнения с прошлой кампанией по респондентам; разница кампаний показывается только при не меньше k ответов в обеих (И-148).
5. Результат: черновик `pmo:maturity` в пространстве компании, аудитория `management` (`draft_artifact`, разделы: итог по измерениям, разрывы, дорожная карта улучшений, которую пишет РПО); маршрут `company_doc`. Пункты дорожной карты становятся задачами правки методологии и наборов, их ведёт РПО. Сверка 32 (С32-02): `insight` документов не пишет (запись вниз у него только `trigger_risk`, `observe_risk`, `00` §3.3, `13` §4.1); черновик создаёт `agents` по событию `maturity_campaign.closed`: читает `insight.maturity_results` и зовёт `cycle.draft_artifact` в пространстве компании в правах закрывшего кампанию РПО.

## 4. Портфель и стратегия (A82)

### 4.1. Стратегические цели и связь проектов

- `office_strategic_goals` (`tenancy`): дерево «цель → подцель», ключ `SG-N`, владелец из руководства, период, показатели `kpis [{name, unit, baseline, target, due}]` (показатель с денежной единицей класса `budget`), аудитория `company` или `management` (умолчание `management`), состояние `draft, active, achieved, retired`. Правит `portfolio/manage_goals` (РПО, Наб области компании; подразделение ведёт свои подцели).
- `office_project_goal_links` (`project`): проект, цель, вклад `direct` или `supporting`, обоснование, состояние `proposed, confirmed, rejected`. Предлагает МП своего проекта (агент предлагает кандидата по паспорту и брифу проекта, решает человек), подтверждает РПО.
- Сверка 32 (У32-08). МП видит и предлагает только цели аудитории `company`; цель аудитории `management` связывает РПО, а МП видит у связи только ключ `SG-N` и пометку «цель руководства» без названия и показателей. Агент-кандидат работает в правах запустившего МП и цели `management` не получает.
- Проект без подтверждённой связи помечается в портфеле «вне стратегии»; это сигнал, не запрет (при `start_requires_decision` решение комитета видит пометку).

### 4.2. Критерии и метод приоритизации

Метод: весовая оценка. Критерии с весами и шкалой хранятся в профиле ПМО (`portfolio_criteria`), потому что они часть методологии и утверждаются вместе с ней.

| Критерий (умолчание набора, компания правит) | Вес (калибровка, не цель) | Источник значения | Класс |
|---|---|---|---|
| Соответствие стратегии | 30 | код: подтверждённые связи (`direct` 5, `supporting` 3, нет 1) | `team` |
| Ценность для заказчика и компании | 20 | оценка людей по шкале 1-5 с якорями; вход `plan:benefits` | `team` |
| Финансовая отдача | 20 | оценка по шкале 1-5 видящими бюджет по `business_case:finance` | `budget` |
| Риск (обратная шкала) | 15 | код: открытые риски `high` и сработавшие, здоровье проекта | `team` |
| Срочность и обязательства | 15 | оценка людей; обязательный проект (закон, договор) помечается `mandatory` и не ранжируется | `team` |

Итог = Σ (вес × значение) / (5 × Σ весов) × 100. Несколько оценщиков дают медиану по критерию; самооценка МП своего проекта помечена и может быть пересмотрена РПО с причиной. Ничья решается критерием «соответствие стратегии». Без `plan.budget/view` итог считается без финансового критерия с пометкой «без финансового критерия» (И-143).

### 4.3. Цикл портфеля, сценарии, решения комитета

1. **Цикл** (`office_portfolio_cycles`): область (компания или подразделение), период, председатель; состояния `draft, scoring, review, decided, closed`. Периодичность из методологии (умолчание ежеквартально, калибровка, не цель).
2. **Оценка**: оценщики ставят значения ручных критериев; код считает вычисляемые; ранг и итог в правах зрителя.
3. **Сценарии** (`office_portfolio_scenarios`): набор решений по проектам (`start, continue, pause, stop, defer`) и ограничения: ёмкость ролей по месяцам (§4.4), конверт бюджета (`budget`). Код считает: сумму итогов, покрытие целей (сколько итога приходится на каждую цель), спрос по ролям против ёмкости (перегруженные месяцы), бюджет против конверта (только видящим бюджет). Кнопка «предложить» строит жадный вариант кодом (по убыванию итога, обязательные первыми, пока ограничения соблюдены); модель сценарий не строит. Сверка 32 (У32-05): сценарий это разностный инструмент (переключение одного проекта показывает его часы по ролям и деньги через перегруз и конверт), поэтому клетки `portfolio/scenarios` и `portfolio/decide` дополнительно требуют `plan.budget/view` (закреплено, как `procurement/view_offers`), а сценарий с конвертом бюджета целиком класса `budget`.
4. **Заморозка**: `POST /portfolio/cycles/{id}/freeze` сохраняет ревизию каталога отчётов (`office_reports`, область цикла, режим `snapshot`, гранты комитету по классам); решения ссылаются на неё.
5. **Решения** (`office_portfolio_decisions`): по проекту или сценарию: `approve_start, continue, pause, stop, reprioritize, change_goal_link, other`, обоснование, участники, ссылка на замороженную ревизию; состояния `recorded, executed, superseded`. Исполнение: человек делает операцию владельца (`project.approve_start`, переход статуса проекта `POST /projects/{pid}/status` (`03` §3.1), `project.decide_goal_link`) и отмечает решение `executed` со ссылкой на событие (И-144). Сверка 32 (У32-16, С32-04): `project.approve_start(project, decision_ref)` требует клетку `project/approve_start` (РПО, наблюдатель области; у МП нет); `ui` перед вызовом читает у `insight`, что решение `approve_start` по этому проекту записано и заморожено, и передаёт его ключ; `insight` по `project.start_approved` отмечает решение `executed`, при несовпадении ключа пишет `portfolio.decision_mismatch` в аудит.
6. **Текст для комитета** это результат `portfolio_review` аудитории `management` конвейера `26` (таск 115): пакет фактов кодом, сценарист и контент-менеджер пишут текст, утверждает РПО.

### 4.4. Ресурсы между проектами (без D06)

- **Спрос по ролям**: `plan.role_demand(project, baseline)` (новое у `plan`): часы по ролям из `wbs_snapshot.hours_by_role` принятой базы, распределённые по месяцам по рабочим дням между плановыми датами пакета (Гант таска 93, производственный календарь §6.3). `insight` суммирует по области.
- **Ёмкость ролей**: `office_role_capacity` (`insight`): область, роль, месяц, часы; вводит РПО (`portfolio/capacity`). Людей, отсутствий и загрузки нет: это D06.
- **Показ**: «роль × месяц: спрос, ёмкость, перегруз». По проекту часы видят только видящие бюджет (УИБ29-17), по области суммой. Сверка 32 (У32-04): зрителю без `plan.budget/view` сумма по области показывается только разрезом «роль × месяц» при не меньше трёх проектах со спросом в ячейке, без фильтров по разрезам `dims` и проекту, со вторичным подавлением соседних месяцев (И-100, И-143).

### 5.2. Уровни, рабочее место, обновление

- **Уровни**: подразделение (наблюдатель области `department` своего подразделения, РПО) и компания (наблюдатель области `company`, РПО). Уровень проекта это существующий экран здоровья (таск 46).
- **Рабочее место руководства**: новый экран «Портфель» `/office/portfolio` рядом с «Отчётами» `/office/reports` (`13` §4.6): вкладки «Обзор» (дашборд области), «Цикл» (оценки, сценарии, решения), «Цели», «Ресурсы», «Мои дашборды». Сохранённый дашборд это `office_dashboards` со списком виджетов с параметрами (область, период, фильтры по `dims`); данных он не хранит. Сверка 32 (С32-06): у таблицы уже есть `cut enum(project, department, company)`, `spec json`, `spec_version`, `source enum(catalog, query)` (`03` §2.11, `12` §4.3), где `catalog` значит фразу по каталогу P13 таска 50; поэтому портфельный дашборд это `source = widgets` (новое значение), область в `cut` (`department` или `company`) и новом поле `scope_id`, виджеты в `spec {widgets: [{key, params}]}` с `spec_version = 2`; отдельных полей `scope`, `widgets` нет. Фильтры виджета только из справочников разрезов; у виджетов W3, W5, W10 фильтры подчиняются правилу §4.4.
- **Обновление (решение)**: живые агрегаты по снимкам. Снимки метрик обновляются по событиям со схлопыванием 1 минута и ночной сверкой (`12` §4.1); виджет считается при открытии в правах смотрящего через `insight.compile_query` с фиксированной спецификацией виджета; экран подписан на `metric.updated` своей области. Сверка 32 (У32-07): события портфеля (`portfolio.*`) несут только ключи без значений и доставляются по `channels.may_deliver` с клеткой `portfolio/view_scores` и областью зрителя; значения экран перечитывает в правах смотрящего. Ревизия (заморозка) нужна только решению комитета и выгрузке и делается через каталог отчётов (§4.3 п. 4).
- **Отличие от G04**: G04 это фраза, по которой агент строит произвольный запрос к живым данным (`POST /dashboards/query`, D03). Здесь виджеты из фиксированного каталога, параметры выбирает человек из списков, модель не участвует. Фраза по каталогу (P13, история 24) и режим `live` отчётов на портфеле остаются в таске 50 среза H.

Класс `budget`. Набор `funding_profile`.

Источник вехи: элемент ИСР вида `milestone` (крупный тип), этап договора `office_contract_stages` (любой тип с договором), у маленького типа без этапов две служебные вехи набора «задание принято» и «сдача». Шаблоны критериев выхода поставляются по видам вех: «старт планирования», «базовый план утверждён», «сдача этапа», «закрытие проекта». Фокусная область акта не закрывает (И-149). Правки внесены в `21`, `22`, `23` с пометкой «A79»; сверка 32 заменила старые имена в `24`, `25`, `26` и дописала блоками в `01`, `03`, `14`, `interfaces.md` (С32-13).

**Реестр вех ворот (сверка 32, С32-01, С32-12).** `cycle` стоит ниже `plan` и `contracts` и читать их не может (`00` принцип 12), поэтому вехи для ворот хранит своя таблица `office_gate_milestones` (`cycle`): `project_id`, `key` (`MS-N`, не переиспользуется), `source enum(preset, wbs, contract_stage)`, `source_ref`, `title`, `planned_date?`, `state enum(planned, passed, cancelled)`. Пишет её только `cycle.register_milestone(project, source, source_ref, title, planned_date?)`, которую зовут сверху вниз: `plan` при принятии базы и правке вехи ИСР, `contracts` в `set_contract_stages`; служебные вехи набора (`source = preset`: «задание принято», «базовый план утверждён», «сдача») пишет сам `cycle` при выборе набора. До таска 43 (F) и таска 44 (G) у всех типов действуют служебные вехи; когда появляются вехи ИСР и этапы договора, служебная веха с тем же видом получает `cancelled` с причиной «заменена вехой MS-N». `<веха>` в видах `gate:<веха>`, `act:stage-<веха>`, `stage_report:<веха>` это ключ `MS-N`. `cycle.check_gate(project, milestone_key)` проверяет пункты кодом; первый зелёный результат по вехе даёт событие `gate.passed (project_id, milestone_key)` (его слушают подписки `26` §5.6 и виджет W9).

**Как применяется к агентам и облаку.**
- Профиль `office_ai_policy_profiles` (`tenancy`) действует после принятия версии, у которой он во входах (как профиль ПМО, И-141).
- `routing.resolve` отклоняет класс задач или релиз вне профиля (409 `policy_forbids`); запуск агента уходит в `paused` с причиной.
- `agents.assign` проверяет класс профиля агента до постановки.
- `tenancy.propose_cloud` и `tenancy.confirm_cloud` (`28` §4.1, §9.2; сверка 32, С32-05: в `31` было имя `propose_cloud_enablement`, такой операции нет; политика проверяется на обоих шагах, потому что между предложением и подтверждением её могли сузить) отклоняют классы задач и данных шире `cloud.max_*`; сужение политики ниже действующего включения облака сужает его до пересечения и уведомляет АдмК и ОПД.
- Шаблон вида с `review_policy` ниже `review_floor` не публикуется (422 `review_floor`). Сверка 32 (У32-15): уже опубликованные виды не обходят порог: действующая политика ревью считается при каждом маршруте, публикации и слиянии как большее из `review_policy` вида и `review_floor`, без переписывания шаблонов.
- Настройки проекта (`export_ban`, маршруты моделей проекта) только сужают профиль.
- Закреплённые запреты (`pii_check` только локально, классы `budget`, `management_chat`, `personal`, `usage` наружу никогда, `28` §4.2) политика не открывает (И-145).
- Сверка 32 (У32-13). Локальные системные классы `pii_check` и `embed` не входят в `allowed_task_classes`: политика сужает только их облачный вариант (`pii_check` в облаке и так запрещён); иначе запрет остановил бы приём всех каналов (И-107 «детектор недоступен: запись ждёт»), а это отказ вместо деградации (принцип 10).
- Сверка 32 (У32-14). Чат Claude Code панели не проходит `routing.resolve` (`28` §3.7), поэтому профиль несёт `chat_allowed_max`: `office_companies.settings.sovereignty.chat_allowed` не шире профиля; внешние клиенты MCP ограничены `external_clients_content_max` (И-119).
- Истёк `valid_until`: баннер у РПО, АдмК, ОПД, показатель зрелости И9 краснеет; поведение не отключается (принцип 10 «деградация, не отказ»).
- Без принятой политики действует профиль по умолчанию: текущие настройки компании.

### 7.2. Проверки на предвзятость модели

**Набор.** В золотые наборы `02` §11 и `28` §3.5 добавляется набор предвзятости: синтетические входы с подстановкой признака, который не должен менять вывод: имя (мужское и женское, имена разных языковых групп), возраст в тексте, должность (младший и старший), сторона (заказчик и команда), регион, размер компании заказчика. Не меньше 200 пар на класс задач (калибровка, не цель). Подход сравнения пар общий для проверки моделей; конкретный стандарт не выбирался (не проверено).

Сверка 32 (У32-12). Модели платформы видят не имена, а метки `⟦Слово-N⟧` (`28` §5.4, И-106), и `28` §3.5 требует наборы с метками. Поэтому пары варьируют признаки, которые переживают псевдонимизацию: грамматический род слов вокруг метки («⟦Участник-3⟧ предложил» и «предложила»), возраст и стаж в тексте, должность, сторону (заказчик или команда), регион, размер компании, языковую форму текста; имя как признак не варьируется. Отдельная проверка: исход не зависит от номера и слова метки. Набор компании собирается только из текстов после `pseudonymize` и проверки детектором ПД (И-107), хранится классом `team` и не покидает контур; поставляемый набор синтетический.

| Класс задач | Что сравнивается в паре |
|---|---|
| `extract` (кандидаты требований, рисков, поручений) | набор извлечённого по ключам, тяжесть и вероятность |
| `doc_review`, `senior_check` | число замечаний и их тяжесть к тексту, который отличается только автором |
| `elicitation` | число и характер вопросов (словарь кода: вопросы о компетентности, о личном) |
| `report`, `draft_text`, `assistant` | упоминание признака без надобности, отказ и полнота ответа; тон по словарю как мягкая метрика |

**Метрики и пороги** (калибровка, не цель): доля пар с разным исходом не больше 5 процентов; средняя разница числовых оценок не больше 0,2 по шкале 1-5; доля ненужных упоминаний признака не больше 2 процентов. Первые две жёсткие (ворота), третья и тон мягкие (видны в отчёте).

**Кто и когда запускает.**
- Поставщик платформы: эталонный прогон в пакете весов.
- Компания: автоматически в приёмочном Ц-В1 вместе с качеством (таск 127); при смене модели, квантования, скила класса; перед активацией наложения компании для затронутых классов (таск 112; красный прогон даёт 409 `bias_failed`); периодически заданием `core` по `bias.cadence_days` (умолчание 90 дней, калибровка, не цель); вручную АдмК или ОПД (`ai/run_bias_check`).
- Облачная модель проверяется только на поставляемом синтетическом наборе и только при действующем включении облака для этого класса; свой набор компании только локально (И-146).

**Ворота и связь с Ц-В1.** `office_model_evals.suite enum(quality, bias, injection)`; класс задач на релизе включён, только если последние прогоны `quality` и `bias` этого релиза на этом железе зелёные (`office_model_class_gates.state = enabled`). Красный периодический прогон переводит класс в `suspended`: `routing.resolve` берёт следующий разрешённый релиз или отвечает отказом с деградацией по `28` §3.2; уведомление АдмК, ОПД, РПО. Результаты видят АдмК, РПО, ОПД; итог в разделе 7 политики, виджете W10 и показателе И9.

Сверка 32 (С32-08). Ворота по `bias` действуют на закреплённом кодом перечне классов, которые обрабатывают тексты о людях (`extract`, `doc_review`, `senior_check`, `council_member`, `council_arbiter`, `elicitation`, `report`, `draft_text`, `assistant`, `search_answer`); `bias.gate_classes` политики может перечень только расширить. Классы `embed`, `pii_check`, `code`, `browser_check`, `design` проходят только `quality`: набора предвзятости для них нет, и иначе они не включились бы никогда. Облачный релиз после включения облака стоит в `blocked`, пока не пройдут поставляемый эталон качества и прогон `bias` на синтетическом наборе; до того `routing.resolve` берёт локальный релиз.

Платформа не оценивает и не ранжирует людей (`30` М-13); набор проверяет то, что она делает с текстами о людях.

### 7.3. Учёт вклада человека и модели

**Что считается по каждому пункту версии** (единица как у ревью по пунктам `25` §6.2: абзац по `lineage`, строка таблицы, элемент списка):

| Вид пункта | Как определяет код |
|---|---|
| `model_unchanged` | Пункт ввёл коммит агента (ветка `agent/<run>/…`) или прямая версия `draft_artifact` (вызов модели с `request_key`), человек его не менял, ревью `accepted` |
| `model_edited` | Пункт ввела модель, затем коммит человека изменил его или ревью `edited` |
| `model_refuted` | Пункт модели опровергнут ревью (`refuted`) и удалён до принятия |
| `human` | Пункт ввёл коммит человека |
| `mixed` | Пункт человека переписан коммитом агента и принят |

- `knowledge.paragraph_origins(version)` отдаёт по `lineage` вид автора коммита, который ввёл и последним менял пункт (агент `agent-<run>`, система с `request_key`, человек `user-<id>`), без имён.
- `cycle.record_contribution(version)` по событию `document.version_created` и `version.accepted` объединяет это с решениями `office_review_items` и пишет `office_contribution_records`: счётчики по видам пунктов, запуски агентов (`run_id`), роли людей (не личности). `office_review_items` получает `origin_kind`, `origin_run_id` при открытии ревью.
- **Связь с журналом запусков и ревью**: каждый `run_id` ведёт в журнал запуска (`02` §3.5: модель, скил, класс, входы); доля опровергнутых пунктов уже питает автовыбор модели (`12` §3.3, `25` §6.4).
- **Показ**: вкладка «Вклад» у версии («модель ввела 62 процента пунктов: принято без правки 40, исправлено 18, опровергнуто 4; человек 38»; числа пример); сводка проекта по видам артефактов и периодам; портфель агрегатом по проектам (W10). Роль в сводке показывается только при не меньше 3 людях этой роли в выборке (калибровка, не цель), иначе «команда».
- **Без слежки**: персональный вклад (`/me/contribution`) видит только сам человек; API чужого персонального вклада нет (404 всем, включая АдмК и АдмП); вклад не входит в метрики здоровья, светофор, отчёты и дашборды по людям, оценки команды (П-С8 не строится), выгрузки (И-147). Кто принял конкретный пункт, видно в ревью этого артефакта как и сейчас: это подотчётность артефакта, а не учёт вклада.
- **Сверка 32 (У32-06).** Карточка версии показывает только виды пунктов, без `by_role` (у версии с одним автором роли разбивка равна личному вкладу); сводка проекта только по фиксированным периодам (календарный месяц, квартал, весь проект), без произвольных дат и без фильтра по автору, со вторичным подавлением: если роль скрыта в одном периоде, она скрывается и в объемлющем, чтобы разность периодов её не раскрыла (И-100); ни один API не группирует и не фильтрует вклад по автору версии или MR. Персональный вклад считается на запрос из `knowledge.paragraph_origins` по `user-<id>` самого запросившего и не хранится отдельной таблицей.
- Заказчику учёт вклада не показывается (раскрытие ИИ заказчику пользователь не включил, §14).
