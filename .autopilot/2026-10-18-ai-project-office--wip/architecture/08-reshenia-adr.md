## ADR-01. 14 модулей, зависимости только вниз

**Контекст.** Офис это раздел текущей панели (R07). Файлы называли модули по-разному, вызовы шли вверх.
**Решение.** `src/office/`: `core`, `tenancy`, `routing`, `knowledge`, `bridge`, `project`, `cycle`, `plan`, `contracts`, `delivery`, `channels`, `insight`, `agents`, `ui`. Один писатель на таблицу. Зависимость вниз по графу 00 §3.3, вверх только события и задания `core`.
**Альтернативы.** Отдельный сервис и SPA: противоречит R07, дублирует вход и установщик. Девять модулей спецификации: вызов модели, транзакция и очередь нужны ниже `agents`, договоры размазаны.
**Последствия.** Плюсы: модуль тестируется отдельно, шов приёмки один (`cycle`). Минусы: обратная связь только событиями. Долг: границы `interfaces.md`.
**Статус.** Принято; пересмотрен A43 (2026-10-23): модулей 15, пятнадцатый `ops`, действует ADR-73. **Ссылки.** R07, A43; 00 §3; 03 §2.0; 05 §3.1, §9.2; ADR-73.

## ADR-02. `agents` над доменом

**Контекст.** Агент действует правами назначившего (G06, G22) и пишет в несколько модулей; вызов из `cycle` давал цикл.
**Решение.** `agents` над доменом и под `ui`: второй вход с теми же операциями и проверками, без публикации, принятия, одобрения и слияния документа. Домен будит агента событием или заданием `core`; ревьюер-агент отвечает `cycle.review_doc_mr` с `reviewer_kind=agent`.
**Альтернативы.** Агент ниже `cycle` возвращает предложение: вызвавший становится копией агента. Отдельный сервис агентов: дубли прав и развёртывания.
**Последствия.** Плюсы: нет циклов; права это пересечение прав назначившего и профиля; откат по `run_id`. Минусы: отладка событий. Долг: тесты изоляции до среза C.
**Статус.** Принято. **Ссылки.** G06, G22, G23; 02 §1-2; 03 И-22; 05 п. 2, 9.

## ADR-03. `routing` как шлюз модели; ключ только компании

**Контекст.** Модель зовут `knowledge`, `cycle` и `agents`; нужны лимиты и выбор модели по классу (G11, G12). Источник ключа открыт (P02).
**Решение.** `tenancy` хранит ключи, строки по классам (`draft_text, extract, check, doc_review, code, browser_check, search_answer`), лимиты и доли. `routing` делает `resolve`, `reserve`, `call`, `settle` и ведёт `office_usage`. Ключ компании, подразделения или проекта по цепочке; ключ пользователя и подписка физлица агентом не используются; в джейл ключ подставляет прокси.
**Альтернативы.** Списание в `tenancy`: шлюз оказался бы выше `knowledge`. Внешний маршрутизатор: данные уходят третьей стороне. Ключ пользователя: против P02.
**Последствия.** Плюсы: сверх лимита вызов не уходит (429); отчёт по классам. Минусы: резерв по потолку занимает лимит. Долг: ответ юриста меняет только источник ключа.
**Статус.** Принято; источник ключа ждёт юриста. **Ссылки.** G11, G12, P02, P19; 02 §6; 03 §2.3; 05 п. 4.

## ADR-04. Одношаговые вызовы через `ClaudeBridge` с `max_turns=1`

**Контекст.** Извлечению, ядру, ответу и протоколу инструменты не нужны; срез A запрещает пакет `anthropic`; служебная подсказка Claude Code влияет на цену и задержку (К27).
**Решение.** До замера `routing.call` идёт через `ClaudeBridge` (SDK, `max_turns=1`, без инструментов). Запуски агентов через Claude Code в джейле. Мост получает модель и усилие на запуск, инструменты, политику файрвола, ключ сессии `office-run:<run_id>`.
**Альтернативы.** Прямой клиент API сразу: против решения среза A, вторая авторизация. Всё через многоходовый Claude Code: ломает оценки цены.
**Последствия.** Плюсы: один транспорт. Минусы: возможная лишняя задержка. Долг: замер обоих путей.
**Статус.** Принято; ждёт пилота P20, затем решение пользователя. **Ссылки.** 01 §7.8; 02 §4.1, О2; 05 Н5.

## ADR-05. Два раздельных Git

**Контекст.** Документы в Git с MR, ревью и откатом (A10-A12); Git для кода не строить (A14); Git документов внутренний без интеграций (A15).
**Решение.** Документы: голый репозиторий `<данные>/office/git/<company>/<project>.git`, пишет только `knowledge` через git CLI за `DocRepo`; нет сервера, клона, push, зеркала, вебхуков. Код: только внешний GitHub или GitLab через `delivery`, коммиты и MR приходят источниками. Общих таблиц, веток, прав и событий нет.
**Альтернативы.** `docs/` в репозитории кода: смешивает Git, правила кода против маршрута. Документы на GitHub или GitLab, зеркалом или основой: запрещено A15, заказчик там не ревьюит. pygit2, dulwich: системная libgit2 или слабое слияние.
**Последствия.** Плюсы: заказчику и аналитику не нужна учётка на хосте. Минусы: ещё один объект копии. Долг: git 2.38+ (иначе слияние во временном дереве).
**Статус.** Принято пользователем. **Ссылки.** A10-A12, A14, A15; 00 §3.4; 01 §3.2; 03 И-33; 04 §2.

## ADR-06. Канон текста: две равные копии

**Контекст.** HANDOFF: «Markdown в базе и в поиске»; A10: «ещё и в Git». Файлы расходились, где канон.
**Решение.** Текст версии хранится блобом Git и колонкой `markdown`, связаны `blob_sha` и `content_sha`. Номер и статус только в базе. При порче верна копия, совпавшая с `content_sha`; строка без коммита получает коммит, коммит без строки получает строку по трейлерам.
**Альтернативы.** Канон только в Git: против HANDOFF, поиск и права по файлам. Канон только в базе: Git становится вторым оригиналом без правил восстановления.
**Последствия.** Плюсы: обе формулировки пользователя выполнены. Минусы: двойная запись. Долг: сверщик и `version.repo_mismatch`.
**Статус.** Принято. **Ссылки.** A10; 00 §3.4; 03 И-02; 05 п. 17.

## ADR-07. Версия = слияние MR; маршрут по версии; метка `accepted`

**Контекст.** MR разных авторов (A11); заказчик видит документ на отмеченном статусе (G52); принятое не переписывается.
**Решение.** Версия это коммит первой родительской цепочки `main`, изменивший один файл; номер при рождении. Одна слитая правка = одна версия `draft`; коммиты ветки не версии; «сохранить» прямой записи (`brief`, `page`, соло) даёт версию. Маршрут по неизменяемой версии: `draft, internal, customer, accepted, returned, signed`. Принятие ставит `accepted/<doc>/v<N>` (не подпись, P09). Откат `restore_version` или `revert_doc_mr` даёт новую версию.
**Альтернативы.** `main` только принятое, слияние после маршрута: заказчик согласовывал бы невидимую ему ветку. Версия на каждое сохранение: засоряет маршрут. Один `git revert`: не даёт текст K.
**Последствия.** Плюсы: заказчик видит только версии. Минусы: номера у заказчика с пропусками. Долг: миграция 0006.
**Статус.** Принято. **Ссылки.** A11, A12, G52, P09; 01 §3.2; 03 §3.2; 05 п. 18-23, 32.

## ADR-08. Правила MR документов

**Контекст.** Ревью разных авторов (A11), минимум ручного труда, агент ничего не принимает (G23).
**Решение.** Одобряется голова MR; новый коммит начинает раунд. Нужно одобрение человека не автора плюс владельцы задетых разделов, иначе менеджер. Сливают менеджер или владелец; автослияния документов нет; `--no-ff`, без squash и rebase, обновление ветки слиянием `main`. Соло маленького типа с аудитом. Зачёт ревью за внутренний шаг роли X, если каждый MR после прошлого прохождения шага одобрен человеком этой роли; заказные шаги без зачёта.
**Альтернативы.** Одобрение по коммиту: оставлено инструментом ревьюера. Автослияние по P07: текст для заказчика сливает человек. Менеджер всегда обязателен: узкое место.
**Последствия.** Плюсы: нет двойного согласования. Минусы: зачёт сложнее объяснить. Долг: экран конфликта по абзацам.
**Статус.** Принято. **Ссылки.** A11, G23, G107; 03 §2.6, §3.9; 05 п. 24-28.

## ADR-09. Журнал намерений `office_git_intents`

**Контекст.** У Git и SQLite нет общей транзакции; ссылки двигаются и без коммита (закрытие ветки, метка, приёмка агента).
**Решение.** Таблица `office_git_intents` (`knowledge`). Порядок: объекты Git; намерение `pending`; `update-ref` со старым значением (отказ: `aborted`, 409 `stale_head`); транзакция версии и `applied`. Записи проекта под файловой блокировкой `DocRepo`, по одной. Проверка при старте до приёма запросов и раз в минуту.
**Альтернативы.** Колонка `state` в `office_doc_commits`: не покрывает сдвиги без коммита. Только ночная сверка: окно расхождения до суток. Серверный хук Git: не видит транзакцию базы.
**Последствия.** Плюсы: восстановление однозначно по фактической ссылке. Минусы: ещё таблица. Долг: тест обрыва в каждом окне.
**Статус.** Принято. **Ссылки.** К06, К07; 00 §3.4; 01 §3.2; 03 И-09; 05 Н4.

## ADR-10. Агент во временном клоне

**Контекст.** `git worktree` делит ссылки с голым репозиторием: агент мог бы сдвинуть `main`.
**Решение.** `knowledge` вне джейла клонирует одну ветку `agent/<run_id>/<doc>` в каталог запуска; голый репозиторий не монтируется. `import_agent_commits` забирает коммиты в `refs/quarantine/<run>`, проверяет пути, автора, трейлеры, слияния и секреты, двигает ветку по журналу намерений. Код так же: клон и пуш делает `delivery`, бот пишет только в `agent/*`.
**Альтернативы.** `git worktree`: см. контекст. Снимок файлов без истории: теряется правка по требованиям. Правка только через API: Claude Code работает с файлами.
**Последствия.** Плюсы: `main` и метки агенту физически недоступны. Минусы: клон на каждый запуск. Долг: тест враждебной инструкции.
**Статус.** Принято. **Ссылки.** К08; 01 §3.2; 02 §3.6, §4.4; 05 п. 8.

## ADR-11. Каталог данных офиса вне `PROJECTS_DIR`

**Контекст.** Чат читает файлы своих проектов; документы рядом обошли бы видимость.
**Решение.** База, Git документов, квитанции, медиа, экспорт и каталоги запусков вне `PROJECTS_DIR`, вне корня файлового менеджера и `confine_root`. Чат получает данные офиса только через API или MCP с правами пользователя.
**Альтернативы.** Рядом с проектами под правами ОС: чат работает под той же учёткой. Отдельный сервер данных: лишний для одного сервера.
**Последствия.** Плюсы: права не обойти через чат. Минусы: второй каталог в установщике и стенде. Долг: проверка установщиком.
**Статус.** Принято. **Ссылки.** К22; 00 §5; 03 И-34; 04 §2.3.

## ADR-12. Джейл для всех сессий чата

**Контекст.** Без песочницы чат под учёткой сервиса видит сервер. Пользователь выбрал вариант 1.
**Решение.** Каждая сессия чата, включая админа и белый список, только в джейле с файрволом и только со своими проектами; база и каталог офиса не монтируются. Без bubblewrap установщик ставит веб без чата. Запуски агентов: `require_jail=True`, своё сетевое пространство, выход через прокси с белым списком, без файла подписки владельца. Без джейла только разработка на macOS.
**Альтернативы.** Джейл только для ограниченных сессий: отвергнуто пользователем. Отдельный сервер чата: дорого.
**Последствия.** Плюсы: чат и инъекции не выносят данные. Минусы: требования к ОС. Долг: тесты сети и ключа до среза C.
**Статус.** Принято пользователем. **Ссылки.** A23; К22, К24, К25; 00 §6; 02 §4.4; 04 §2.3.

## ADR-13. `Embedder` и распознавание речи с переключением

**Контекст.** Claude не даёт эмбеддингов и не распознаёт речь. Пользователь: оба варианта, локальный и внешний, с переключением (A17, A24). Вывоз текста под вопросом 152-ФЗ.
**Решение.** В `knowledge` два шва: `Embedder` (`kind local, external`, `model_tag`) и распознавание речи (имя `SpeechRecognizer`). Умолчание локальное (эмбеддинги bge-m3 int8). Внешний сервис включает только админ компании подтверждением с аудитом; проект с «запретом вывоза» остаётся локальным. Смена эмбеддингов это фоновая переиндексация; кэш и пороги по `model_tag`. В режиме «только текст» медиа удаляется после распознавания.
**Альтернативы.** Только локально: против A17, A24 и нагрузки слабого сервера. Только внешне: вывоз по умолчанию недопустим. Только расшифровка видеосвязи: не все API её отдают.
**Последствия.** Плюсы: работа без сети. Минусы: память и процессор под модели. Долг: замер на минимальном сервере, установка весов из локального зеркала.
**Статус.** Принято пользователем; вывоз текста ждёт юриста. **Ссылки.** A17, A24; 01 §4.2; 00 §4, §10; 04 §3.

## ADR-14. sqlite-vec, строка вектора на фрагмент

**Контекст.** Права до ранжирования: фильтр после поиска раскрывает число скрытого. Один вектор на текст не проверяет статус версии внутри KNN.
**Решение.** sqlite-vec за `VectorIndex`. `office_embedding_cache(model_tag, text_hash)` хранит вектор один раз; `office_vectors` держит строку на фрагмент с `visibility`, `family`, `version_status`, `is_current`, `model_tag` и секцией проекта. Полный перебор в секции, грубый битовый отбор выше 100 тыс. строк.
**Альтернативы.** LanceDB: вторая транзакция, оставлен запасным. Qdrant: отдельный сервис. Chroma, FAISS: фильтр только после поиска. pgvector: нет PostgreSQL.
**Последствия.** Плюсы: одна транзакция с фрагментами. Минусы: версия до 1.0. Долг: проверка загрузки расширения.
**Статус.** Принято. **Ссылки.** К19; 01 §4.3; 05 Н7.

## ADR-15. Гибридный поиск, RRF, без переранжирования до золотого набора

**Контекст.** Слова ловят ключи и числа, векторы перефразы; стеммер FTS5 английский.
**Решение.** FTS5 по леммам pymorphy3 и сырому тексту (0,7 и 0,3), векторы, ядра документов; слияние RRF k=60, топ 20; соседи и шаг по рёбрам; бюджет 6000 токенов. Переранжирование выключено, пока на золотом наборе nDCG@10 не вырастет на 5 пунктов при p95 до 1,5 с; для «сверить» включено.
**Альтернативы.** Взвешенная сумма: несравнимые шкалы. Переранжирование всегда: задержка без доказанного выигрыша. GraphRAG: пересказ вместо цитаты, дорогая генерация.
**Последствия.** Плюсы: дёшево и детерминированно. Минусы: качество на русском не измерено. Долг: золотой набор из P20.
**Статус.** Принято; пороги ждут пилота P20. **Ссылки.** G76-G80, A13; 01 §4.4, §7, §9.

## ADR-16. Абзацы, линия, проверка цитаты

**Контекст.** След и комментарии держатся за абзац; кандидат без дословной цитаты недопустим.
**Решение.** Нарезка по структуре: абзац, строка таблицы, пункт списка (`kind`), реплика, файл диффа. Id `p-<sha1[:12]>-<n>`, `lineage` переносится картой (`same, moved, changed, removed, added`, порог 0,6). Цитата одного формата (документ, версия, коммит, абзац, линия, смещения, текст, таймкоды); проверка одна, `knowledge.verify_quote`, без модели.
**Альтернативы.** Фиксированный размер: нет якоря. Смысловая нарезка: граница плавает. Утверждения от модели: не дословно.
**Последствия.** Плюсы: переиндексация только изменённого. Минусы: неровные единицы. Долг: `split` таска 03, миграция 0008.
**Статус.** Принято. **Ссылки.** G104, G112, истории 41, 51, 52; 01 §3.3, §5; 05 §3.10.

## ADR-17. События через `office_events`

**Контекст.** Шина в памяти теряет событие при перезапуске; задания идут в другом процессе.

## ADR-18. Одна очередь `office_jobs`

**Последствия.** Плюсы: один экран ошибок. Минусы: два процесса-писателя SQLite. Долг: нагрузочная проверка.
**Статус.** Принято. **Ссылки.** К37; 00 §4; 02 §3.3.

## ADR-19. SQLite на одном сервере, путь роста

**Контекст.** On-premise у студии; чаты уже на SQLite.

## ADR-24. Заказчик не видит внутреннее

## ADR-25. Бюджет видят менеджер и руководство

## ADR-26. Трекер: только выгрузка и статус

**Контекст.** Внешний трекер расширяет, а не заменяет платформу; одно подключение в первом выпуске (P06, A16).

## ADR-27. Почта через корпоративные ящики

## ADR-30. Хранение без срока

**Контекст.** Пользователь: «без ограничения по времени» (A20); Git неизменяем, 152-ФЗ даёт право на удаление.

**Альтернативы.** Сроки по умолчанию: отвергнуто пользователем. Источники в Git: удаление по закону переписывало бы историю.
**Последствия.** Плюсы: полная история для споров. Минусы: рост диска. Долг: способ вычистки подтверждает юрист.
**Статус.** Принято пользователем; удаление по 152-ФЗ ждёт юриста. **Ссылки.** A20, К11; 00 §7; 01 K2; 03 В-13.

## ADR-34. PMBOK и Agile двумя слоями; история задач с первой задачи

**Контекст.** Бриф требует PMBOK вместе со Scrum и Kanban (07 п. 3); сгорание, поток и освоенный объём нельзя восстановить задним числом.
**Решение.** Управленческий слой (паспорт, требования, ИСР, оценки, бюджет, база, риски, изменения скоупа) и поставочный (бэклог, спринты или поток, доска) связаны через требование, элемент ИСР и задачу. Тип проекта задаёт глубину первого слоя, методика форму второго. `office_task_history` (`cycle`, только добавление) пишется с среза C в транзакции изменения.
**Альтернативы.** Один слой «всё задачи»: нет бюджета и базы. История из событий `office_events`: события не хранят прежних значений полей.
**Последствия.** Плюсы: отчёты Scrum и Kanban и будущий освоенный объём на одной истории. Минусы: рост таблицы. Долг: нет.
**Статус.** Принято. **Ссылки.** 09 §1, Р-01, Р-02; 07 п. 3.

## ADR-35. Замена базового Jira и Confluence

**Контекст.** 07 п. 4: у страниц нет дерева и пространств, нет сохранённых фильтров и досок.
**Решение.** Страница `page:<n>` с постоянным номером, дерево и порядок в базе, пространство это проект. Сохранённый вид это структурный фильтр по белому списку полей, фраза переводится в него, запрос к данным не генерируется. Доска только группирует статусы 05 §3.4, своих статусов нет. Подписки на объекты у `channels`.
**Альтернативы.** Дерево путями Git: перенос переименовывал бы файл и ломал след. Свой язык запросов: против P13. Свои статусы досок: ломают согласия и сверку.
**Последствия.** Плюсы: базовый набор закрыт без нового модуля. Минусы: нет пользовательских полей и процессов (В-6). Долг: пространство компании (В-1), ввоз из Jira и Confluence после выпуска.
**Статус.** Принято; пространство компании ждёт пользователя. **Ссылки.** 09 §2; 05 §6 С23, С24.

## ADR-60. Браузер для людей: расширение в браузере пользователя; серверный Chromium для людей H1-H3; P23 сохраняется для серверного (пересмотрен A38, действует ADR-70)

**Пересмотрен A38 (2026-10-23).** Слова пользователя «единое рабочее место со своим собственным браузером ... внешний браузер только для сторонних программ» снимают умолчание «расширение как основной путь, серверный Chromium для людей в H». Действующее решение: ADR-70 (браузер платформы гибридом в первом выпуске, расширение равноправным вторым клиентом по A40). Текст ниже сохранён как история.

**Контекст.** A27 просит превью во «встроенном браузере Хромиум» с плагинами магазина Chrome и доступом к содержимому любой страницы как сайдбар ассистента, по аналогии с расширениями ChatGPT, Codex и Claude в Chrome. P23 давал браузер только агенту и на стенд; 10 §13 ждал решения по H1-H3 (В10-05). Слова пользователя новее.
**Решение.** Первый выпуск: превью результатов встроено в SPA (pdf.js, таблица с сервера, расшифровка, iframe отчёта; C, D) и расширение «Ассистент офиса» (Manifest V3, боковая панель `chrome.sidePanel`) для Chrome и Chromium-браузеров, принимающих расширения магазина (G): страница читается по действию человека (адрес, заголовок, выделение, основной текст Readability, только видимое), уходит в платформу как `page_context`, источником становится только кнопкой «импортировать страницу» (`web:<хэш адреса>`, карточка B); токен клиента `extension` с областью «ассистент»; запрещённые адреса задаёт админ компании; распространение скрытой публикацией и политикой `ExtensionInstallForcelist`. Серверный Chromium для людей: H1 браузер стенда для демо с журналом (H); H2 белый список внешних адресов и H3 профиль пользователя с входами отложены до ответа юриста и отдельного узла. P23 для серверного браузера в первом выпуске не меняется.
**Альтернативы.** Серверный Chromium с расширениями магазина для людей сразу (вариант Б 13 §3.3): сторонний код расширений рядом с данными офиса, SSRF и выход от IP студии, куки чужих систем на сервере, 0,5-1 ГБ на сессию; отклонено для первого выпуска. Только превью без расширения: не закрывает «любую страницу» и «плагины».
**Последствия.** Плюсы: сервер и данные офиса не затронуты, расширения любые у человека, P23 цел. Минусы: сборка и публикация расширения, аккаунт магазина из РФ (Q13-3); боковую панель в Яндекс Браузере проверить. Долг: юрист по чтению сторонних страниц (Q13-8).
**Статус.** Пересмотрен A38 (2026-10-23): действует ADR-70; Q13-2 закрыт словами A38 и A40. **Ссылки.** A27, A38, A40, P23, G98; 13 §3; 10 §13; 02 §9; 05 §7 С99; 05 §8 С110; ADR-70.

## ADR-61. Отчёты: спецификация агентом по каталогу наборов, компилятор и рендер у `insight`, модель видит ряды в правах автора; каталог с грантами и классами данных; `ExportRenderer` у `knowledge`

**Контекст.** A29 просит, чтобы агент строил HTML-отчёты с визуализацией по текстовому запросу из всего контекста проекта; A30 просит каталог с правами доступа и экспорт в HTML, PDF, Word, Excel. **Решение.** Агент `report_builder` (класс `report`, `agents`) получает каталог наборов данных в правах автора (`insight`, код: метрики, требования, задачи, риски, ИСР по A22, созвоны, документы, сверки, расход, граф) и ряды через `dataset_query` (до 2 000 ячеек) и пишет спецификацию `spec_version=1` (факты, секции `text`, `kpi`, `chart`, `table`, `graph`); SQL, HTML и JavaScript модель не пишет. `insight.compile_report` проверяет по схеме и белому списку, `render_report` подставляет числа из фактов кодом, сверяет `[n]` через `verify_quote`, рисует Vega-Lite; показ в iframe `sandbox` без `allow-same-origin`. **Альтернативы.** Генерация SQL моделью: обход прав. Модель не видит ряды (12 §4.2): текст отчёта без значений не отвечает A29. Отдельный движок вёрстки (WeasyPrint): второй вид документа.
**Последствия.** Плюсы: пересмотр P13 только в границах раздела, ядро P13 (нет генерации запроса) цело; один шаблон для экрана и экспорта. Минусы: около $0,40 за отчёт; каталог наборов растёт по срезам. Долг: D03 для портфеля остаётся отложенным (фраза по живым данным, `POST /dashboards/query`, `live` на портфеле).
**Статус.** Принято пользователем (A29, A30; пересмотр P13 и D03 в границах раздела); срез G ждёт подтверждения (Q13-1). **Ссылки.** A29, A30, P13, D03, A22; 13 §4; 12 §4; ADR-51; 05 §7 С77, С94, С100; И-46.

## ADR-64. Документы скоупа семейством `spec`; эксплуатационная документация `guide:admin` и `guide:role-*`

**Контекст.** A33 называет документы скоупа ТЗ, ЧТЗ, ФТТ; A34 называет руководство администратора и руководства пользователей по ролям. Комплект знал один `spec` и один `guide`; В10-06 ждал пользователя.
**Решение.** Виды `spec` (ТЗ), `spec:chtz-<слаг>` (ЧТЗ), `spec:ftt` (ФТТ) одним семейством с одной нумерацией `REQ-NNN`, одним маршрутом `spec` и ролью якоря `refines`; `has_version` для P10 смотрит вид `spec`. ## ADR-65. Коммит к задаче по ключу в сообщении, ветке и MR; связь по смыслу `proposed`; хронология проекцией `office_timeline_items` на d3

**Контекст.** A33 просит хронологию изменений кода и макетов с обратной трассировкой на документы скоупа. Код живёт только во внешнем GitHub или GitLab (A14), часть коммитов без ключа задачи.

**Последствия.** Плюсы: трассировка по времени, а не по текущему состоянию. Минусы: ещё одна проекция и задание пересборки. Долг: доля коммитов без ключа у студий (В14-12), дифф кода модели при `export_ban` к юристу (В14-08).

## ADR-66. Страж цепочки: обнаружение в `cycle`, предложения существующими профилями, запись только через MR, версии и маршруты; режим `gate`

**Контекст.** A34 и A35: когда задача поставлена мимо цепочки (сообщение заказчика в Telegram без требований в ТЗ, ЧТЗ, ФТТ), агенты должны сопоставить исходные требования при постановке любой задачи, предложить дополнения и записать изменения, сохранив версионность и граф. И-22 запрещает агенту сливать и принимать.
**Решение.** `cycle.check_chain` по триггерам (постановка задачи, изменение требования, коммит без связи, версия макета, прогон, закрытие спринта, ночной проход) находит разрывы видов `no_requirement`, `requirement_not_in_scope`, `scope_not_accepted`, `no_mockup`, `mockup_outdated`, `no_test`, `no_guide`, `orphan_code`, `orphan_mockup_change`, `ahead_of_scope`, сопоставляет с требованиями кодом и моделью (T1 0,92, T2 0,80), оценивает `ui_impact`, пишет `office_chain_gaps` и части `office_chain_gap_items`. Скил `chain_keeper` ставит запуски существующих профилей (аналитик, дизайнер, тестировщик, писатель) с целью `{gap_id, part}`; дополнения к одному документу скоупа склеиваются в один MR с трейлером `Office-Gap`. Запись только существующими операциями владельцев: кандидат, ветка агента и MR, маршрут, `register_mockup`, `save_scenario`; разрыв закрывает только `check_chain` (И-40), человек может лишь снять с причиной. Режим `gate` (умолчание крупного типа) держит `awaiting_approval → handed` при открытом блокирующем разрыве раньше `on_approval` (409 `chain_gap_open`, И-43); задача уходит в работу после отправки версии заказчику. Части, требующие веток агента, строятся в E; обнаружение, кандидаты и `gate` в C.
**Альтернативы.** Страж пишет в `main` и след напрямую: ломает И-22 и ADR-07. Отдельный модуль или рантайм стража: дубль агентов. Блокировать до принятия заказчиком: простой команды; оставлено вопросом В14-02.
**Последствия.** Плюсы: цепочка восстанавливается автоматически, человек решает по частям; граф и версии целы. Минусы: ложные разрывы при плохих порогах (ориентир снятий не выше 15%); расход около $0,10 на спорное сопоставление. Долг: В14-01-В14-03 у пользователя, пороги на P20.
**Статус.** Принято пользователем (A34, A35); одобрение MR стража менеджером, момент отпуска `gate` и умолчание `gate` ждут пользователя; пороги ждут пилота P20. **Ссылки.** A34, A35, И-11, И-19, И-22; 14 §6; 09 §4; 10 §8.1; ADR-43; 05 §7 С72, С85, С102; И-39-И-43.

## ADR-67. План на завтра через кандидатов: источники каналов, извлечение одношаговым `extract`, приоритет и укладка кодом, вечерняя сборка, чужой план по матрице

**Контекст.** A36 просит в планировщике с календарём конвейеры чтения событий календаря, почты и мессенджеров для плана работ менеджера на следующий день и такой же план каждому участнику с правкой перетаскиванием. ## ADR-68. Рабочее место одним ядром раскладки на dockview; `office_ui_layouts` у `tenancy`; реестр виджетов кодом

**Контекст.** A37 просит интерфейс как у Claude Code, VS Code и Cursor: слева проекты и файлы, по центру диалог или встроенный браузер с иконкой панели чата, справа виджеты и подсказки, всё настраивается по положению и размеру. 04 §6 описывал три рабочих места с общим каркасом.

Мобильный вид стопкой с нижней полосой; клавиши `Mod+K`, `Mod+P`, `Mod+Shift+L`, `Alt+1..4`. Из AI-Workspace переиспользуются `Sidebar`, `FileTree`, просмотрщики, терминал, тема и `ws.ts`; `OfficePage.tsx` заменяется каркасом.

**Последствия.** Плюсы: один каркас для команды, заказчика и наблюдателя; смена библиотеки не трогает сохранённое. Минусы: dockview слабее по клавиатуре у разделителей, закрывается командами палитры; большая переделка фронта в C. Долг: доступность с диктором на P20 (В15-16).

Дополнение A38: вкладка `browser` живая с E (ADR-70), адресная строка центра одна для всех видов (05 §8 С111). **Ссылки.** A37, A38; 15 §2; 04 §6-7; 12 §7; ADR-54; ADR-70; 05 §7 С70, С92, С95; 05 §8 С111.

## ADR-70. Браузер платформы как основа рабочего места: гибрид; один движок, два хоста; расширения по допуску; единый протокол «страница → ассистент → артефакты» с двумя клиентами

**Контекст.** A38: «единое рабочее место со своим собственным браузером, который покрывает все потребности проектной команды для работы с проектами, проектной документацией и кодом; потребность во внешнем браузере только для сторонних программ». A27 просит Chromium с плагинами магазина Chrome и доступ ассистента к содержимому любой страницы; A37 ставит браузер в центр рабочего места; A40 просит плагины для внешних браузеров с сопоставлением увиденного со всеми артефактами проекта. ADR-60 ставил расширение в браузере пользователя основным путём, а серверный Chromium для людей откладывал в H до юриста и отдельного узла. Слова пользователя новее.
**Решение.** Гибрид (13 §3.2): внутреннее содержимое (документы, версии, превью, страницы, макеты, прототипы, экраны, отчёты) рисует платформа во вкладках `document`, `preview`, `screen`; внешнее (стенд, GitLab и GitHub, трекер, сайты белого списка компании) открывает серверный Chromium узла браузера (`ai-workspace-office-browser`, по процессу на сессию под bwrap с cgroup, шов `BrowserHost` у `agents`) с трансляцией по протоколу отладки и вводом по WS во вкладку `browser`; одна адресная строка на все виды. Сеть узла только через прокси с белым списком `office_browser_allowlist` (`tenancy`; системные строки от подключений, `no_context`, запрет частных диапазонов и перепривязки DNS). Расширения магазина Chrome грузятся в серверный профиль из каталога `office_browser_extensions` по допуску админа с проверкой подписи CRX, автообновления выключены, сеть расширений через тот же белый список. Профиль сессии на tmpfs, при сне шифруется `SecretBox`, по концу сессии удаляется; `persist_logins` после юриста. Один движок с браузером запуска агента (образ Playwright, формат `browser_action`, клиент трансляции), два хоста: `BrowserRunner` (`delivery`) в джейле запуска только на стенд, `BrowserHost` (`agents`) для людей. Единый протокол «страница → ассистент → артефакты» (13 §3.7: захват в режимах `manual`, `match`, `full`; политика `tenancy.browser_policy`; `insight.match_artifacts` кодом; вопрос ассистенту с контекстом в рамке «внешний материал»; импорт `web:*` и привязка карточками B) с двумя равноправными клиентами: вкладка `browser` и расширение «Ассистент офиса» для Chrome и семейства и Firefox (Safari в H). P23 остаётся для запусков агентов; H1 и H3 входят в первый выпуск; H2 отложено до юриста и P20. Срезы: внутренние виды C, узел и протокол E (таски 77, 78), каталог расширений и расширение G (таски 79, 76), `watch` и Safari H.
**Альтернативы.** Только серверный Chromium (как Claude in Chrome, браузер Cursor) для всего: удвоение памяти и задержка на собственные экраны платформы. Изолированный iframe с переписывающим прокси: не держит расширения, ломает CSP, service worker, OAuth и встраивание большинства систем. Расширение в браузере пользователя как единственный путь (ADR-60): не «единое рабочее место», входы и расширения вне контроля компании. Один хост для агента и людей: браузер агента вышел бы из джейла запуска к белому списку компании. Действия ассистента на внешней странице сразу: инъекция под входом человека управляла бы сторонней системой.
**Последствия.** Плюсы: сервер и данные офиса отделены от стороннего кода (узел без данных офиса, только профиль и прокси); расширения под допуском админа; одни и те же компоненты ассистента в вкладке и в расширении; контекст с любой страницы в реальном времени сопоставляется с артефактами без модели. ## ADR-71. Контекст собирается онлайн по ходу работы; ни одна рабочая задача не требует выхода из платформы

**Контекст.** A39: «ключевой подход архитектуры: контекст по рабочим вопросам, созвонам и задачам собирается в режиме онлайн; новый AI-first подход и UI/UX по всем ключевым рабочим областям управления проектами по PMBOK». A41: «все 100% рабочих задач и вопросов решать не покидая платформы и не оставляя снаружи проектный контекст, который влияет на скоуп, результаты и документацию». 13 §2 описывал импорт файлов как путь внешнего контекста без оговорки о его месте.
**Решение.** Принципы 15 и 16 в 00 §2. Контекст попадает в ядро по ходу работы: созвоны адаптерами (11 §3), папки ящика и группы с ботом (11 §5, 15 §1.1), задачи и доска, документы в редакторе с MR, стенд и коммиты вебхуками (14 §5), страницы трекера, репозитория и внешних систем протоколом «страница → ассистент → артефакты» из вкладки `browser` и расширения (13 §3.7) с режимами `match` и `full`; импорт файлов (13 §2) это запасной путь для того, что родилось снаружи. Проверка по 10 областям знаний PMBOK (05 §8.3) и по ролям (05 §8.4): пробелы названы и совпадают с отложенным словом пользователя (D06: Гант, учёт времени, загрузка, документооборот, внешние календари) или решены по замыслу (созвон с камерой у поставщика, подпись в документообороте, IDE по желанию), и каждое исключение возвращает контекст в платформу. Адрес вне белого списка не открывается молча во внешнем браузере: карточка с заявкой админу и кнопкой «открыть внешне», чтобы выход из платформы был видимым и редким.
**Альтернативы.** Импорт постфактум как основной путь: контекст теряется между событием и импортом, авторство и время размываются. Автоматический сбор всего, что человек видит в браузере, без режимов: против приватности и 152-ФЗ, юрист не ответил. Запрет внешнего браузера совсем: созвон с камерой и подпись на сервере не живут.
**Последствия.** Плюсы: один критерий полноты для всех разделов; пробелы перечислены, не скрыты. Минусы: режимы `match` и `full` дают юристу новые вопросы; живая расшифровка по ходу созвона ждёт поставщиков. Долг: таблица 05 §8.3 пересматривается при снятии D06.
**Статус.** Принято пользователем (A39, A41); режим `full` по умолчанию ждёт юриста (Q13-13). Дополнение 2026-10-23, A41-A45: карта ролей дополнена работами DevOps и перепиской в чатах проекта (05 §9.5), исключения по замыслу: консоль поставщика VPS до адаптера, однократная команда подготовки сервера под `root`, ручная отправка с личного аккаунта; A41 в `in-spec`. **Ссылки.** A39, A41, A38, A40; 00 §2; 05 §8.3, §8.4, §9.5; 13 §2, §3.7; 11 §3-§5; 14 §5; 17 §4-§5; 18 §5; ADR-70, ADR-73, ADR-78.

## ADR-72. Лестница способов импорта; Playwright-сценарий во вкладке автоматизации браузера платформы как последняя ступень

**Контекст.** A46: «модули импорта позволяют загружать данные в ручном и автоматическом (дельтами, по веб-хуку) режиме по API-ключам и MCP-серверам; при недоступности этих методов пользователь открывает систему во встроенном браузере и в отдельной вкладке автоматизирует выгрузку Playwright, не покидая рабочее место». 13 §2 знал только файлы, 04 §1 адаптеры только с API.
**Решение.** Пять ступеней в один конвейер ядра (13 §2.7): ручная загрузка (`knowledge`), API-ключ (адаптер `bridge`), MCP-клиент (новый вид адаптера `bridge`: инструменты только чтения внешнего MCP-сервера, bwrap с сетью к хосту), вебхук и дельты по курсору (`bridge`), Playwright-сценарий во вкладке автоматизации браузера платформы (`agents`, 13 §3.12): человек входит сам во вкладке `browser`, записывает действия (формат `browser_action`, локаторы по дереву доступности, без паролей) или описывает выгрузку ассистенту (одношаговый черновик класса `browser_check`), пробный запуск под трансляцией, затем раннер без модели исполняет шаги формата 10 §2 в той же сессии над `BrowserHost`; результат в `office_uploads` и карточку привязки; сценарий `office_import_scenarios` с курсором и расписанием («дельта без API», интервал от часа); при закрытой сессии запуск ждёт входа; ночные дельты только при хранении входа после юриста (Q13-12). Один ключ повтора источника на всех ступенях, переход между ступенями без дублей.
**Альтернативы.** Сценарии в джейле запуска агента (`BrowserRunner`): там нет входа человека и белого списка компании. Сценарий пишет и исполняет модель: дорого, недетерминированно, против принципа 8. Хранить входы для ночных дельт по умолчанию: против Q13-12. Расширение во внешнем браузере как исполнитель: нужны `<all_urls>` и `debugger`, браузер человека занят, расписания нет.
**Последствия.** Плюсы: любая система без API подключается за полчаса руками пользователя; довод в пользу серверного Chromium (ADR-70) усиливается; данные идут обычным конвейером с правами. Минусы: хрупкость к смене вёрстки (починка локатора по подтверждению), ночные дельты ждут юриста, сценарии, меняющие данные во внешней системе, требуют явной галочки (Q13-17). Долг: замер устойчивости на P20.
**Статус.** Принято пользователем (A46); ночные дельты и сценарии с записью во внешнюю систему ждут юриста и пользователя (Q13-12, Q13-17). **Ссылки.** A46, A38; 13 §2.7, §3.12; 10 §2, Р10-01; 04 §1; 02 §7; 00 §3.2; 05 §8 С123; ADR-70.

## ADR-73. Пятнадцатый модуль `ops`: над `bridge`, `project`, `knowledge`, `routing`, под `delivery`, `insight`, `agents`; события сборки и выкладки разбирает `ops`

**Контекст.** A43: «CI/CD процессы + работа с докер-контейнерами, VPS-серверами, мониторинг состояния железа и составных модулей, отдельный модуль платформы». ADR-01 закреплял 14 модулей; сборку MR разбирал `delivery` (уточнение 20 spec), стенд жил в настройках проекта (P01), здоровья модулей платформы не было.
**Решение.** `src/office/ops/` пятнадцатый модуль (17 §1): пайплайны и задания CI, окружения и развёртывания, реестры, серверы и выдачи, шим, контейнеры, терминал, журнал команд, ряды телеметрии, оповещения, здоровье модулей; швы `CiProvider`, `ServerTransport`, `MetricsSource`, `RegistryClient`. Зависит от `bridge` (подключение кода, `register_handler`), `project`, `knowledge` (`ingest_source`), `routing`, `tenancy`, `core`; с `cycle` не связан (ключи задач строками, цепочку до требования строит `insight.back_trace`). Выше его зовут `delivery` (`stand`, `pipeline_state`, `request_deploy`, `admin_inputs`), `insight` (чтение `metrics`, `dora`, `deployed_scope`), `agents` (инструменты и карточки B), `ui`. Вызовов вверх нет: здоровье модулей выше `ops` реестром проб `core.register_probe` и `run_probes`; красная сборка будит агента событием `pipeline.finished`; `delivery` пишет `ci_state` по тому же событию. Одно подключение кода, два обработчика событий хоста через `bridge.register_handler(system, kinds, fn)`: коммиты, MR, ревью у `delivery`; пайплайны, задания, развёртывания у `ops`. Срезы (05 §9 С125): B пробы и телеметрия платформы (таск 81), F CI/CD и агент DevOps (82, 83), G серверы, мониторинг, режим `platform`, прод (84, 85); до F разбор `check_suite`, `status` у `delivery`, миграция `ops_ci` переключает источник без смены API.
**Альтернативы.** Эксплуатация внутри `delivery`: модуль разросся бы до сверки, кода, макетов, ролика и серверов разом, а серверы компании не принадлежат проекту. Эксплуатация как внешний сервис: против A41 (работа внутри платформы) и принципа 1. Срезы по 17 §10 (C, E, F, G): ярусы C и E полны (16 тасков T3).
**Последствия.** Плюсы: один писатель состояния сборки и выкладки, стенд и прод видны в платформе, DORA и риск «стенд недоступен» из одного ряда; `delivery` беднее на один протокол. Минусы: ещё один модуль в графе и пакете разработчика; два обработчика одного подключения требуют тестов маршрутизации по `(system, kind)`. Долг: В17-01 (срез), В17-17 (роль).
**Статус.** Принято пользователем (A43); срез и роль ждут пользователя. **Ссылки.** A43, A41, A14, P01, P07, P22; 17 §1, §2.2, §10, §11; 00 §3; 04 §1.4; 05 §9 С124, С125, С128; ADR-01 (пересмотрен), ADR-31, ADR-57.

## ADR-74. CI и образы снаружи; два режима выкладки; сервер через шим с принудительной командой и закреплённым ключом хоста; терминал только человеку с записью

**Контекст.** A14 (код только во внешнем хосте), A23 (песочница), P01 (стенд разворачивает внешний CI), сервер-ориентир 4 ядра и 16 ГБ; студии держат стенды на VPS разных поставщиков, часть за NAT.
**Решение.** Своего раннера и реестра нет: сборка, тесты, образ и выкладка идут во внешнем GitLab CI или GitHub Actions, образы в реестре хоста или OCI компании (`oci_v2`); платформа читает, запускает, повторяет, отменяет, одобряет (17 §2.1, §3.1). Два режима выкладки: `ci` (умолчание, P01: развёртывание рождает событие хоста или задание `deploy_*`) и `platform` (`docker compose` по SSH через шим, образы только по дайджестам, `office.override.yaml` с метками проекта и окружения, секреты окружения через stdin). Сервер доступен ключом платформы с `restrict,command="…/shim"`: белый список глаголов, JSON-ответ, действия только над контейнерами с метками своего проекта и окружения (И-49); ключ хоста закрепляется подтверждением админа, несовпадение блокирует сервер (И-51). Прод (`protected=1`) только после одобрения другим человеком или соло маленького типа (И-50); агенты и ассистент прод не запрашивают и не одобряют. Терминал к серверу только человеку с правом и причиной, отдельным ключом без `command=`, запись вывода asciicast в `BlobStore`, ввод не пишется, сессия до 60 минут; код asyncssh и компонент терминала переиспользуются из чата, профили чата не переносятся (05 §9 С150). Поставщики серверов: ручной ввод, API отложено до слова пользователя после пилота.
**Альтернативы.** Свой раннер в платформе: `docker build` чужого кода рядом с базой и ключами, Docker в bwrap требует привилегий, ресурсы сервера-ориентира. Свой реестр `registry:2`: диск, TLS, копии. Произвольные команды по SSH вместо шима: нет белого списка и журнала. Kubernetes: вне рамок до слова пользователя.
**Последствия.** Плюсы: чужой код не исполняется рядом с данными офиса; наименьшие права на сервере; откат это повтор прошлого развёртывания. Минусы: зависимость от CI хоста (токен запуска, доступность реестров из РФ); режим `platform` требует стек compose на сервере; за NAT сервер недостижим до `push_agent`. Долг: В17-02, В17-03, В17-06, В17-07, В17-09; юрист В17-10, В17-12; пилот В17-13-В17-15.
**Статус.** Принято; части ждут пользователя, юриста и пилота P20. **Ссылки.** A14, A20, A23, P01, P07, P22; 17 §2, §3, §4; 00 §4.1, §6; 03 И-48-И-54; 05 §9 С127, С129, С150; ADR-11, ADR-12, ADR-21.

## ADR-75. Мониторинг шимом без демона; `telemetry.db` отдельным файлом с уровнями хранения; здоровье модулей реестром проб `core`; оповещения конвейером; DORA и риски у `insight`

**Контекст.** A43 «мониторинг состояния железа и составных модулей»; A20 (хранение без срока); Н17 (один файл SQLite); ADR-48 (один конвейер уведомлений); ADR-38 (один движок метрик).
**Решение.** Метрики сервера и контейнеров раз в 60 секунд глаголом `metrics` шима по SSH (пул с keepalive, до 8 параллельных сборов, одна команда в минуту на сервер); проба HTTP окружения, срок TLS раз в сутки; ряды пишет только `ops` в отдельный `<данные>/office/ops/telemetry.db` (SQLite WAL, строка на цель и минуту, значения float32 упакованы): минутные 14 дней как кэш, 5 минут 30 дней, час и сутки без срока; строки уровня удаляются только после свёртки их интервала (И-55); копия 00 §5 берёт свёртки часа и суток раз в сутки. Это исключение из Н17 с причиной: минутная запись 20 серверов не должна удлинять ожидание записи основной базы; оповещения, развёртывания, пайплайны и журналы остаются в основной базе. Здоровье модулей платформы: каждый модуль при старте регистрирует пробы в `core` (`register_probe`), `core` исполняет их, пишет `office_heartbeats` раз в 30 секунд и событие `platform_module.health_changed`; так нет вызова вверх. Логи контейнеров не хранятся: живой просмотр по WebSocket с маской секретов построчно и фрагмент по кнопке в `BlobStore` (`log:<sha>`). Оповещения `office_ops_alert_rules` и `office_ops_alerts` (`firing, acknowledged, resolved, silenced`) уходят только конвейером 11 §6.1: critical `immediate` в обход тихих часов (как `usage.threshold` 100 %), warning в сводку; critical окружения дольше 10 минут даёт источник `incident:<id>` и точку хронологии. `insight` читает `ops.metrics`, `ops.dora` и пишет снимки (`stand_down_minutes`, `stand_availability_7d`, `default_branch_red_hours`, DORA прода); кандидаты рисков «стенд недоступен», «сборка красная», «нестабильные выкладки» через `cycle.trigger_risk` (09 §5).
**Альтернативы.** node_exporter и cAdvisor с Prometheus: службы, порты и своя TSDB вне `tenancy`; толкающий демон на каждом сервере: публичный адрес платформы и установка на чужие серверы (после выпуска для NAT); хранилище логов Loki: объём при A20 и секреты; ряды в основной базе: ожидание записи.
**Последствия.** Плюсы: ни служб, ни портов на серверах; права и журнал в `tenancy`; один движок метрик и один конвейер уведомлений. Минусы: за NAT не работает до `push_agent`; второй файл базы в копии и восстановлении; пороги по умолчанию ждут пилота. Долг: В17-05, В17-11, В17-16.
**Статус.** Принято; В17-05 ждёт пользователя, В17-11 юриста, В17-16 пилота. **Ссылки.** A20, A43; 17 §5, §3.3; 00 §4, §5, §8; 11 §6; 09 §5; 03 И-55; 05 §9 С127, С148; ADR-19, ADR-38, ADR-48.

## ADR-76. Агент DevOps: CI, `Dockerfile` и compose веткой и MR; починка красных сборок классов `config`, `dependency`, `image`, `lint` по `propose`; без секретов, SSH, прода; руководство администратора пишет технический писатель из `ops.admin_inputs`

**Контекст.** A43 и A42 (код и тесты всех разделов, обновление документации); принцип 6 (агент предлагает, человек публикует); 02 §2.2 запрещает агенту разработки правку CI; 10 §8.1 и 14 §2.3 отдают руководства техническому писателю.
**Решение.** Профиль `devops` (02 §2.1, класс `code`, скилы `bundled`: `ci_gitlab`, `ci_github`, `dockerfile`, `compose`, `ci_triage`): по задаче вида `ops` или с требованиями эксплуатации пишет CI по стадиям `office:*`, многоступенчатый `Dockerfile` с непривилегированным пользователем и `HEALTHCHECK`, compose с пределами ресурсов и `${ИМЯ}` вместо значений, веткой `agent/ABC-12-<слаг>` и MR от бота (P22); читает ядро через `search`, `get_fragment` и `ops` только чтением (`list_pipelines`, `job_log`, `environments`, `server_facts`, `lint_ci`). Запрещено: пуш, слияние, SSH, шим, защищённые ветки, выкладка, секреты, правила защиты; проверка без модели: `ops.lint_ci`, `hadolint`, `docker compose config`, сканер секретов; зелёный пайплайн MR это условие приёмки, не одобрение. Починка красной сборки: триггер `pipeline.finished` `failed` с классом `config`, `dependency`, `image`, `lint` на ветке по умолчанию или ветке задачи агента; класс считает код по правилам, сводку пишет `routing.call` классом `extract` по маскированной выдержке (при `export_ban=all_external` только правила); один запуск на `(ref, failure_signature)`, после двух неудач подряд автозапуск выключен до решения ТЛ; умолчание `devops_autofix=propose` (карточка ТЛ); `test` и `build` идут агенту разработки или человеку, `infra` и `secret_missing` оповещением. Руководство администратора агент DevOps не пишет: `ops.admin_inputs(project)` входит в `delivery.guide_inputs(audience=admin)`, раздел пишет технический писатель по строкам правила 10 §8.1 (`deployment.succeeded` прода, `environment.*`).
**Альтернативы.** Агент разработки правит CI сам: смешение прав и рисков (секреты, защита веток). DevOps правит `guide:admin` веткой (17 §2.7 первой редакции): второй писатель одного документа против ADR-43 и ADR-64. Автопочинка `auto` по умолчанию: цикл красных MR без человека.
**Последствия.** Плюсы: красная сборка чинится за минуты карточкой; CI и compose по шаблону компании; один писатель руководств. Минусы: доля лимита как у планировщика (P19); классы падений ждут калибровки. Долг: В17-08, В17-16.
**Статус.** Принято; `propose` или `auto` ждёт пользователя и пилота. **Ссылки.** A42, A43, P07, P19, P22; 17 §2.7, §2.8; 02 §2.1-2.2, §6.4; 10 §8.1; 14 §2.3; 05 §9 С126, С130; ADR-43, ADR-64, ADR-10.

## ADR-77. Проектные чаты мессенджеров: подключение проекта у `channels` по внутреннему ID с подтверждением кодом и уведомлением; одна таблица сообщений и источник `chat` «абзац равен сообщению»; одно извлечение на пачку

**Контекст.** A44: «все проектные чаты заводятся в настройках проекта по внутренним ID внешних платформ, агент читает все сообщения». 15 §1.1 знал группы только как источник «чат за день» для плана дня, 01 §2.2 закрывал день по серверу, `office_channel_inbox` держал личные пересылки; A19 запрещает читать личную переписку; A20 хранение без срока.
**Решение.** `office_project_chats` (`channels`): `platform enum(telegram, max, whatsapp, vk_teams, other)`, `external_chat_id`, `external_thread_id?`, вид `customer, internal, contractor, forwards`, состояния подключения 05 §3.4 (`draft, checking, active, degraded, suspended, off`), `read_scope all, mentions_only, unknown`. Привязка МП по ID (подсказка `/office_id`), одна активная на `(platform, chat, thread)` в установке, форум-группа Claude Code запрещена, подтверждение администратором чата командой `/office_bind <код>` (10 минут), обязательное уведомление участников текстом из `office_companies.settings.chat_consent_texts[]` (юрист В18-02), отказ `/office_optout` оставляет метаданные без текста. Один поток входящих (С65): `on_update` → ключ повтора `(platform, chat, external_message_id, kind)` → квитанция сырого JSON → строка `office_chat_messages` (без срока, A20) → абзац источника `chat` (`external_key = <platform>:<chat>[:<thread>]@<день>` в поясе МП, `paragraph_id = m:<id>`, `scope_tag = chat:<chat_id>`, видимость по участию и клетке `chats`) → `channel_message.received` `kind=group` с `message_id`. `office_channel_inbox` только для непривязанных пересылок и `/plan`; пересылка с проектом переносится в чат `forwards`. Вложения через `office_uploads`, голос через `knowledge.transcribe`, история импортом выгрузки `telegram_export` (G). Шов `ChatPlatform` рядом с `ChannelSender` тем же токеном; порядок в `src/bot`: привязанный чат → личный диалог ассистента или пересылка → форум-группа Claude Code. Одно извлечение на пачку (`extract_chat_items`, `extract`, 2 минуты или 30 сообщений, строгая схема с цитатой через `verify_quote`) питает кандидатов решений и обещаний, реестр запросов и план дня; `extract_plan_candidates` остаётся письмам и пересылкам.
**Альтернативы.** Клиент MTProto от имени сотрудника: читал бы личную переписку (A19, Р15-04). Только фрагменты источника без таблицы: нет ленты, запросов и исходящих с журналом. Два извлечения (план дня и трекер): двойной расход и расхождения. Второе подключение на чат (не у `channels`): против §3.1 и ADR-56.
**Последствия.** Плюсы: переписка это контент проекта в правах; одно извлечение; A41 для переписки. Минусы: Bot API не отдаёт историю до бота и удаления в группах; Макс до проверки `mentions_only`; уведомление в группе заказчика требует юриста. Долг: В18-01, В18-02, В18-03, В18-13.
**Статус.** Принято пользователем (A44); текст уведомления и удалённое ждут юриста; Макс ждёт пилота. **Ссылки.** A44, A19, A20, A21, A36, A41; 18 §1, §2, §4.1; 01 §2.2; 15 §1.1, §1.4; 13 §1.7; 11 §6.2; 03 И-58; 05 §9 С131-С134, С137; ADR-48, ADR-56, ADR-67.

## ADR-78. Решения и поручения кандидатами, запросы `ASK-N` реестром, черновики ответов двумя формами одним вызовом в правах аудитории, отправка только нажатием человека; сводка документом `digest`

**Контекст.** A44: «готовит сводку за период, отслеживает принятые решения и поставленные поручения и открытые запросы, готовит краткую и полную форму черновиков ответов для ручной верификации». Принцип 6, И-45 (ассистент не исполняет уровень C), A21 (заказчик не видит внутреннее), A22 (бюджет), Р13-04 (ассистент в группе молчит).
**Решение.** Профиль `chat_secretary` (02 §2.1, права назначившего). Решение (`decision` от 0,6) и поручение (`assignment` от 0,6) становятся кандидатами `cycle.propose_candidates` с цитатой и `origin=chat`; принимает человек (МП, БА для решений; адресат или МП для обещаний); решение со `scope_impact` даёт кандидата версии требования и пункт `CR` (09 §4.2); поручение заказчика вне цепочки через 3 рабочих дня идёт МП и стражу видом `request_untracked`. Запрос `ASK-N` (`office_chat_requests`, `channels`): `open` от 0,75 или по нажатию, адресат и срок кодом (SLA чата), закрытие кодом по ответу-на или по черновику, моделью от 0,8 с отменой 72 часа, напоминания конвейером 11 §6.1. Сводка: дневная по проекту в `digest_at` и по запросу до 31 дня; модель пишет только темы со ссылками `[n]`, остальное подставляет код из таблиц владельцев; хранится документом `digest` вне Git с версиями, Markdown с фронтматтером; страница в Git только через MR человека. Черновик: один вызов класса `assistant` со строгой схемой `short` (до 300), `full` (до 2 000), `citations`, `assumptions`, `missing`, `commitments`; контекст в правах «отправитель ∩ профиль ∩ профиль аудитории чата» (заказчику по 03 §4.2, внутреннее не попадает вовсе); правило обещаний кодом: срок, деньги, объём без МП или РПО не уходят (`needs_pm`, И-57). Отправка только нажатием отправителя с замороженным `params_sha`: `bot_signed` (бот с подписью «Имя через проектный офис», точный журнал) или `manual_copy` (копия, сверка с сообщением автора); у агентов и MCP операции отправки нет (И-56); из ассистента карточкой `send_chat_reply` уровня B. Ассистент в группе молчит; бот как транспорт публикует уведомление, ответы на две служебные команды и подписанный текст (05 §9 С133). Раздел матрицы `chats` закрыт заказчику; `approve_commitments` только МП и РПО.
**Альтернативы.** Агент принимает решения и ставит задачи сам: против принципа 6. Ответ ботом автоматически на запрос заказчика: против «ручной верификации» A44 и A21. Две формы двумя вызовами: дороже и расходятся в фактах. Сводка полем таблицы: не в RAG (A45).
**Последствия.** Плюсы: ни одно обещание не уходит без МП; запросы заказчика не теряются; журнал отправленного точен. Минусы: пороги и SLA ждут пилота; `bot_signed` в чате заказчика требует упоминания в уведомлении (юрист). Долг: В18-04-В18-10, В18-14.
**Статус.** Принято пользователем (A44); подпись ботом и вывоз переписки ждут юриста; пороги пилота. **Ссылки.** A44, A21, A22, A41, A42, A45; 18 §3, §4, §5, §6.4; 13 §1.5-1.7, §4.7; 09 §4.2; 14 §6.1; 03 И-56, И-57, И-59; 05 §9 С133, С135, С136, С139, С152; ADR-58, ADR-77.

## ADR-79. Ассистент собирает любой артефакт из чата существующими профилями и мастерами карточками B; схема данных новым видом `architecture:db-*`; полный ежедневный контекст через ядро и инструменты; уровень C за человеком

**Контекст.** A42: «встроенные агенты в чат-ботах должны уметь ответить на любой вопрос, обладая полным контекстом всего происходящего ежедневно на проекте, и должны уметь собрать любой проектный артефакт (ТЗ, ЧТЗ, детализированные постановки задач, формирование архитектуры баз данных, программирование и тестирование всех созданных разделов, обновление документации и всех артефактов со сквозной двусторонней трассировкой)». G23 того же пользователя: агент не публикует; И-11, И-45; 13 §1.6 уровни A, B, C.
**Решение.** 13 §1.9: таблица «артефакт → кто собирает → чем → что подтверждает человек». ТЗ, ЧТЗ, ФТТ через мастер документов (10 §12) и профиль «Аналитик»; постановки через нарезку 09 §3 и черновик `origin=request`; схема данных новым видом `architecture:db-<слаг>` (семейство `architecture`, в Git, путь `architecture/db-<слаг>.md`) профилем «Архитектор» веткой и MR с маркерами `req:`, ссылка следа `architecture_paragraph` с ролью `models`, ребро `models`, звено 3а цепочки 14 §2.2, вход агента разработки и ядра по коду; код и тесты через профили «Разработчик» (уточнение 20) и «Тестировщик» с MR от бота и CI через `ops`; документация через стража 14 §6 и правило 10 §8.1; трассировка кодом (ссылки следа, граф, хронология, обратная трассировка, слой `ops`). Всё это ассистент запускает карточками B (`agents.assign`, `start_wizard`, `cycle.slice_tasks`, `refresh:<project>:<doc>`, `check_chain`), а «слить», «опубликовать», «принять», «передать» остаются уровнем C: человек нажимает на экране. «Полный ежедневный контекст»: каждый источник работы попадает в ядро (таблица 13 §1.9 «источник → семейство → срез», новые семейства `pipeline`, `incident`, `log`, `digest`, `report`; проверка при приёмке среза, что нет источника вне ядра); структуру (статусы, числа, риски, CR, решения, план дня, метрики) ассистент читает инструментами 13 §1.4 в правах «человек ∩ профиль». Подсказка стража `no_data_model` для задач с `data_impact` (решение ремесла).
**Альтернативы.** Отдельный «агент-сборщик» с правами на всё: второй рантайм и обход И-45. Ассистент сливает и публикует по фразе: против G23 и маршрутов 03 §3. Схема данных разделом внутри `architecture`: один MR на всю архитектуру при каждой правке таблицы; отдельный вид даёт свой маршрут и след (Q13-18). Контекст только через RAG без инструментов: числа и статусы из фрагментов недостоверны.
**Последствия.** Плюсы: ни одного нового профиля ради A42; артефакты рождаются в тех же ветках, MR и кандидатах, что и у людей; трассировка та же. Минусы: цепочка из чата даёт несколько карточек по мере готовности, без человека не идёт (13 §1.6); схема данных требует маркеров `req:` от архитектора. Долг: Q13-18, Q13-19.
**Статус.** Принято пользователем (A42); вид схемы данных и отчёты в ядре ждут пользователя. **Ссылки.** A42, A41, A45, G23, G84-G87; 13 §1.4-1.6, §1.9; 02 §2.1-2.2; 09 §3; 10 §8.1, §12; 14 §2.2, §6; 12 §5; 17 §2.6; 03 И-45; 05 §9 С140-С142; ADR-58, ADR-64, ADR-66, ADR-36.

## ADR-80. Смысловой обмен между модулями и агентами документами ядра (Markdown с фронтматтером, версия); контекст через RAG; события и очередь технический сигнал «документ готов»

**Контекст.** A45: «общение между модулями происходит в формате MD-файлов + постоянный доступ к контексту из RAG». ADR-06 (канон текста), ADR-17 (события `office_events`), ADR-18 (очередь `office_jobs`), принцип 2 (ядро в центре), принцип 5 (права до ранжирования); часть артефактов жила полями таблиц (спецификация отчёта JSON), событие `channel_message.received` несло текст.
**Решение.** Принцип 17 в 00 §2 и абзац в 01 §1 (05 §9.4): (1) всё, что модуль или агент производит для другого как смысл, существует документом ядра или версией источника с фронтматтером (`key`, `family`, `kind`, `version` или `receipt_sha`, `project`, `author`, `side`, `created_at`, `visibility`, `based_on[]`, `req_keys[]`) и телом Markdown; таблицы хранят структуру для экранов и проверок, не единственный экземпляр смысла; (2) агент получает контекст только через `knowledge.search`, фрагменты и документы в правах назначившего, структурные факты инструментами над операциями владельцев; прямой передачи текста между агентами мимо ядра нет; (3) `office_events` и `office_jobs` остаются транспортом: событие несёт ссылку, очередь ключ; текст в событии только как транспорт входящего личного сообщения до записи (`kind=assistant`, `capture`); (4) вызовы вниз по графу остаются. Обёрнуто: спецификация отчёта (ревизия Markdown с фронтматтером, `spec json` производная копия, источник `report:<rid>:<n>`), сводка падения сборки и инцидент (источники с фронтматтером), сводка чата (`digest`). Оставлено с причиной: журнал `browser_action` (формат исполнителя без модели), строгие схемы одношаговых извлечений (предложение с цитатой на документ, решает человек), отчёт пакета нарезки (задачи уже документы `ticket:`), план дня и диалог ассистента (личные, приватность), черновики ответов (предложение до отправки, отправленное ложится в `chat`), файлы CI и compose агента DevOps (внешний Git, возвращаются `commit:`, `code_mr:`).
**Альтернативы.** Буквально «только файлы Markdown, без событий и очереди»: исчезают идемпотентность, повтор после обрыва и права до ранжирования; файловая шина это очередь без ключей. Всё в таблицах, RAG только для документов людей: артефакты агентов невидимы ассистенту, A42 не выполняется. Отдельная «шина смыслов» (брокер сообщений с текстом): второй канон текста против ADR-06.
**Последствия.** Плюсы: любой артефакт любого агента находится поиском и цитируется с якорем; один канон текста; события тонкие. Минусы: компилятор отчётов получает разбор Markdown (одна попытка исправления остаётся); фронтматтер единого минимума нужен всем писателям; отчёты в ядро по правам классов данных требуют фильтра в `tenancy.scope`. Долг: Q13-19 (все ревизии или только `saved`).
**Статус.** Принято пользователем (A45); отчёты в ядро ждут пользователя. **Ссылки.** A45, A42, A13; 00 §2, §3.3, §8; 01 §1, §2.2; 02 §1; 13 §1.8, §4.3; 15 §1.8; 17 §2.8; 18 §2.1, §3.4; 05 §9 С143-С145; ADR-06, ADR-16, ADR-17, ADR-18.
